# T9 — Harness-native integration strategy: OpenCode and Codex under the frozen AEW boundary

- **Status:** research and design note from the independent architecture review (thread T9, added by the designer's addendum of 2026-10-04). Not governing. Research candidates for the design authority and operator. RESEARCH COMPLETE / IMPLEMENTATION INPUT ACCEPTED.
- **Question:** given the frozen typed AEW action surface (T1) and the engine's authority over legality, which native capabilities of OpenCode and Codex should AEW exploit for execution, UX, context economy, containment, observability or reliability, without creating a second authority path?
- **Evidence classes used in this note, marked in every row:** **[doc]** current primary documentation read 2026-10-04 (OpenCode: `opencode.ai/docs/{mcp-servers,agents,permissions,plugins,server,sdk,skills,config,rules,tools,custom-tools,cli}`; Codex: `learn.chatgpt.com/docs/{app-server,config-file/config-reference,agent-approvals-security,hooks,non-interactive-mode,extend/mcp,build-skills,agent-configuration/subagents,cli/reference}`, the new home of `developers.openai.com/codex/*`, which redirects there); **[pin]** the OpenCode 2.0.18 OpenAPI pinned in `tests/fixtures/opencode/openapi-2.0.18.min.json` (17 paths; `Config.InfoEncoded`, `Permission.Rule`, `Mcp.LocalConfigEncoded`, `Mcp.Protocol`); **[probe]** run in this review (T1's MCP spawn through the Lead projection against the fake 2.0.18 server; T6's `serve` under `--unshare-net`, its startup fetch, and its proxy honouring, on Rocky 8.10); **[inf]** architectural inference; **[rec]** recommendation; **[hyp]** unresolved hypothesis that needs a live probe.
- **Not reopened:** T1 (actions and stages below transport; MCP as the first Lead transport; CLI parity; broker custody), ADR-0009 (the narrow adapter; nothing an adapter reports is evidence), ADR-0011, ADR-0012, `DispatchDecision`, M4-B containment labels.

## 0. The one finding that frames the rest

**The pinned OpenCode 2.0.18 API and the public OpenCode documentation describe different products.** [pin] exposes `/api/session`, `/api/event`, `/api/model`, `/api/agent`, `/api/info`, permissions as `Permission.Rule {action, resource, effect}` rulesets, MCP as `mcp.servers.<name> {type, command, protocol}` with `Mcp.Protocol` `legacy | auto | 2026-07-28`, config keys `agents`, `permissions`, `plugins`, `skills`, `tool_output {max_bytes, max_lines}`, `compaction {auto, buffer, keep}`. [doc] describes `/session`, `/global/event`, `/mcp`, `permission: {read, edit, bash, task, skill, …}` objects, `mcp.<name> {type, command, enabled}`, `tools`, `plugin`, `compaction {auto, prune, reserved}`. The capability probe (`harness/opencode/capabilities.py`) exists because of exactly this: "V2 publishes no stability policy and labels its HTTP API experimental". Codex is more explicit: the app-server is labelled experimental in the CLI reference, `codex mcp-server` was removed in favour of it, and the configuration reference marks a dozen features experimental.

Consequence for every row below: **"documented" means documented for some version; what AEW may rely on is what the pinned binary's own schema advertises**, checked at launch, which is the discipline the adapter already applies and which a Codex adapter must copy (app-server has `generate-json-schema` for exactly this). The registry representation (F13) therefore records capabilities **per adapter per pinned version**, never per product.

## B. Recommended integration profile

### OpenCode (pinned 2.0.18, next pin to be chosen by probe)

- **MUST USE:** one private `serve --stdio` per run inside the supervisor's tree; the capability probe against the served `/openapi.json`; `OPENCODE_CONFIG_CONTENT` projection with `OPENCODE_DISABLE_PROJECT_CONFIG`; session environment replacement; `Permission.Rule` allow/deny only; model and variant pins verified against `/api/model`; `tool_output {max_bytes, max_lines}`; the event stream for telemetry; `mcp.servers.aew` for the Lead (T1).
- **SHOULD USE:** per-agent tool filtering (`agents.<n>.permissions`/`tools`) to hide every tool a role does not need, **once the request-level probe shows schemas leave the request**; a run-private `.agents/skills` directory with the curated skills a card requests (D3, U9), disclosed by the native `skill` tool; the `/api/session/{id}/environment` route for the curated environment (already); `interrupt` and inbox delivery (already).
- **OPTIONAL:** `compaction` tuning after measurement; `opencode attach` for a second operator view; the `question` tool for the Lead only (never for runs).
- **DELIBERATELY DO NOT USE:** `ask` permissions in runs; `task`/subagents (until F13's grant); project plugins and `.opencode/` directories in runs; session resume as AEW recovery; `share`; `autoupdate`; LSP and formatter in runs (already off; both fetch and write); the remote `.well-known/opencode` configuration layer.
- **NEEDS LIVE PROBE:** request-level effect of tool filtering; whether `OPENCODE_DISABLE_PROJECT_CONFIG` covers `.opencode/plugins` and the `.well-known` fetch; the plugin API's `experimental.session.compacting` presence in the pinned version; the catalog behaviour with a configured provider and no network (T6 part 3).

### Codex (no pin yet; app-server protocol v2)

- **MUST USE:** `codex app-server --listen stdio://` per run under the supervisor's tree (or `unix://` inside a T6 network sandbox); `initialize` with `experimentalApi: false` and a pinned generated JSON schema as the capability fixture; per-run `CODEX_HOME` with `--ignore-user-config --ignore-rules`; `shell_environment_policy.inherit = none` + `set` = `agent_env`; `approval_policy = never` for runs with `sandbox_mode = workspace-write`, `network_access = false`, `writable_roots` ⊆ the M4-B layout; `turn/interrupt`; `thread/tokenUsage` telemetry; `[mcp_servers.aew]` for the Lead with `required = true`, `enabled_tools` = the T1 catalog, `startup_timeout_sec` tuned.
- **SHOULD USE:** `enabled_tools`/`disabled_tools` to narrow every MCP server to a role's need; `tools.<tool>.output_token_limit`; `outputSchema` for the F19 raw arm; `.agents/skills` curated per run; `features.network_proxy` domain rules as a **second** egress line behind T6's proxy (it filters command execution only [doc]); the native sandbox as defence in depth, recorded as a second line on the run label.
- **OPTIONAL:** `PostToolUse` hooks for artifact capture **if** the probe shows they can run as the supervisor's user outside any decision path; `thread/fork` for the Lead's own exploration; `approvals_reviewer` never.
- **DELIBERATELY DO NOT USE:** `danger-full-access`; `--dangerously-bypass-approvals-and-sandbox` outside the Rocky VM lab; `approval_policy = on-request` or `auto_review` in runs; `features.multi_agent` in runs until F13; `thread/resume` as AEW recovery; `features.memories`; `codex login` state shared across runs; hooks that return `decision` or `updatedInput`; `history.persistence = save-all` outside the run directory.
- **NEEDS LIVE PROBE:** nested bwrap (Codex's inside AEW's) on EL8; `shell_environment_policy.set` yielding exactly `agent_env` (conformance custody scenario 2); hooks' host-side execution context; the app-server's behaviour over `unix://` under `--unshare-net`; whether `enabled_tools` removes schemas from the request (Codex documents the budget, not the removal).

## D. Initial support target: what "AEW supports OpenCode / Codex" means

**Minimum conformance (both):** the harness-neutral scenarios of `harness-conformance.md` §2 pass against the real binary (the live lane), plus the acceptance scenarios AT-14..AT-17; the capability probe against the pinned schema fails closed on any gap; the custody properties hold (no credential, provider key or server secret in any model-controlled process or file); allow/deny only; private instance per run; effective model equals the pin; `stopping_a_run_ends_every_process_it_started` passes on Linux under the M4-B layout; the new "nothing else loaded" scenario passes.

**Optional enhanced capabilities (declared per pin, never assumed):** request-level tool filtering; curated native skills; native sandbox as a second line (Codex); `tool_output` limits; `outputSchema` for raw arms; `unix://` transport under network containment.

**Degraded but correct:** a harness without a capability runs with the fallback column of the matrix and the run label says so (the F13 vocabulary `UNSUPPORTED`): no skills → the card's skills are reported unavailable (today's rule); no native sandbox → AEW's layout alone, label unchanged; no `interrupt` → `terminate`; no event stream → polling (already the rule). Nothing degraded changes a gate, a transition or a label's truthfulness.

**Version and protocol compatibility:** one pinned version per adapter at a time (`TESTED_VERSIONS`), with the pinned schema in `tests/fixtures/<harness>/`; a new version is adopted by regenerating the fixture, re-running the live lane, and updating the matrix's evidence column; MCP protocol revisions negotiated (`Mcp.Protocol` on OpenCode; `initialize` on Codex) with the server declaring what it speaks (T1's four revisions).

**Live smoke (per pin, before "supported"):** server start and probe; one scripted run through the bridge with evidence ingested; the Lead projection loads and `aew lead mcp` is spawned and answers `tools/list`; a run under the M4-B layout on Rocky 8.10; the "nothing else loaded" scenario; cost telemetry present in the run log.
