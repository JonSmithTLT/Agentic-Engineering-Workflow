# T9 live probe 1 — what tool schemas reach the model from OpenCode 2.0.18, with `aew lead mcp` spawned for real

- **Status:** probe results from the independent architecture review, 2026-10-04, answering the first item of `TRIAGE.md` §3 and T1's remaining live check (`T1-typed-lead-surface-design.md` §9). Observed facts, marked **[probe]**; the rest is inference **[inf]** or recommendation **[rec]**.
- **Where:** the Rocky 8.10 VM, review venv, a frozen checkout of `dcd43f1` with the T1 patch applied (`~/aew-review/dcd43f1`, commit `05163af` there), OpenCode 2.0.18 (`opencode-cli`), Python 3.11. Script: `repro/t9/tool_request_probe.py`; console: `tool_request_probe.out.txt`; the captured model requests `request_V*.json` (first turn) and `request_V*_turn2.json` (second turn, 10 s later) were examined on the VM and are not published, being mostly the harness's own system prompt and carrying prompt-cache keys; this note reports what they contained.
- **Method:** the built-in `openai` provider is redirected at a fake endpoint on the host loopback (`providers.openai.settings.baseURL`, the 2.0.18 spelling; it worked first time) that logs each request body and answers 500, so no model ever runs. The Lead projection (`lead_config()` from the T1 branch) is served through `OPENCODE_CONFIG_CONTENT` with private XDG state; the `aew-lead` agent is prompted once per variant. A real AEW project is created under `~/.aew-test-tmp/review-*` and the Lead seat acquired for it, so the MCP server has a credential in its own environment (direct mode); the credential never touches a file and the seat is released at the end. The model request's `tools` array and `instructions` text are the measurement.

## 2. What this settles

1. **T1's MCP transport needs one more line.** On 2.0.18 the Lead projection's server entry must carry `codemode: false`, or the model never sees the typed tools as tools: it sees five of twelve signatures in a catalog and is told to script calls through `execute`, a JavaScript runtime, with the known upstream failure modes (the model not calling `execute`; permission asks from inside Code Mode never surfacing; the catalog dropping a namespace between turns; "Unknown tool" in fresh sessions). The pinned schema has the key (`Mcp.LocalConfigEncoded.codemode`); the capability probe should require it. **[rec]** Applied on the review branch as a follow-up commit (see §4).
2. **T9's largest open row is closed:** per-agent permission `deny` removes a tool's schema from the model request on 2.0.18, for built-in tools and for MCP tools exposed directly. Tool filtering is a real context-cost control, not only an execution gate. The "registry representation" for `tools.filter.per_agent` can state `removes_schema: true` for this pin.
3. **The context cost of the T1 surface is now measured, not estimated:** 11,178 bytes for twelve tools, with `aew_ticket_draft` alone at 3,212 (its schema carries the Ticket's fields). Two-tool acceptance (T1 §12 Q1) and whether to expose `cli` (Q2) can be decided with these numbers.
4. **A new fact for the conformance suite and the T9 matrix:** OpenCode 2.0.18 exposes a built-in **desktop `browser` namespace (45 tools)** through Code Mode whenever `execute` is allowed. For runs the projection's `deny *` hides it (V6). For the Lead, whose rules are `* ask`, it is present: a Lead model can drive a browser with an operator prompt per call. That is a capability the projection should name explicitly (allow with `ask`, or deny) rather than inherit; and the "nothing else loaded" scenario proposed in `T9-harness-native-integration.md` §C should assert the absence of `execute` and `browser` in a run's request, which V6 shows is achievable.
5. **A failed MCP server degrades silently (V4).** The adapter's existing rule for runs, "a failed capability probe fails closed", has no counterpart for the Lead's MCP server: nothing in the session reports that `aew` is missing. **[rec]** `aew opencode` should verify, after the TUI starts, that the server was spawned and answered `tools/list` (the broker sees the first `lead.tool` or a probe call), and say so; the T1 note's §12 gains this as question 7.

## 3. What it does not show

- No model turn ran: whether a model **uses** the direct tools well is the F15 evaluation question (T1 §10), not a transport one.
- `tools/call` through the spawned server was not exercised here; T1's integration tests exercised it against the fake server inside a real Lead session.
- The Code Mode `search()` path was not driven (no model).
- Codex was not probed; the second live probe in `TRIAGE.md` §3 (the app-server handshake with `dynamicTools`) stands.
