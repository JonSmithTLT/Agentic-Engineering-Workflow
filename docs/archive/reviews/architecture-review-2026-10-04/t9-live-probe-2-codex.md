# T9 live probe 2 — the Codex app-server (codex-cli 0.160.0): handshake, `aew lead mcp` spawn, and what reaches the model

- **Status:** probe results from the independent architecture review, 2026-10-04, completing the first item of `TRIAGE.md` §3 (the Codex half). Observed facts are marked **[probe]**; inference **[inf]**; recommendation **[rec]**.
- **Where:** the Rocky 8.10 VM. Codex was installed for this probe with the operator's permission, under `~/aew-review/codex/` only (no sudo, nothing on `PATH`): the `codex-package-x86_64-unknown-linux-musl.tar.gz` release asset of `rust-v0.160.0` (SHA-256 `4fcc47ab…a16b71`; its `.sigstore` bundle saved beside it), which contains `bin/codex`, `bin/codex-code-mode-host`, a bundled `bwrap` and `rg`, and voice assets. `codex app-server generate-json-schema` produced the protocol schema (651 definitions; the v2 file, 611 KB, is copied to `repro/t9/codex-app-server-protocol.v2.schemas.json` as the fixture candidate a Codex adapter would pin). Script: `repro/t9/codex_appserver_probe.py`; console: `codex_appserver_probe.out.txt`; captured model requests: `repro/t9/codex_request_C*.json`.
- **Method:** a private `CODEX_HOME` with a `config.toml` that selects a custom provider pointed at a fake Responses API endpoint on the host loopback (`[model_providers.probe] base_url, wire_api = "responses", env_key`), `approval_policy = "never"`, `sandbox_mode = "read-only"`, `features.hooks = false`, `shell_environment_policy.inherit = "none"`, `history.persistence = "none"`; the `aew` MCP server declared with `env_vars = ["AEW_LEAD_TOKEN", ...]` so the lab project's Lead credential is forwarded from the app-server's environment and never written to a file. The app-server speaks newline JSON-RPC over stdio. No model ever runs.

**What the model receives in every variant** (`codex_request_C1.json`): the `additional_tools` item with three namespaces: `functions` (`exec` 14,662 bytes, a JavaScript "Code Mode" runtime whose description declares the nested tools `apply_patch`, `exec_command`, `write_stdin`, `view_image`, `create_goal`/`get_goal`/`update_goal`, the three MCP resource tools and `clock__curr_time` as TypeScript signatures; `wait`; `request_user_input`; `request_user_input_async`), `clock` (`sleep`), and **`collaboration` (6 sub-agent tools: `spawn_agent` 2,750 bytes, `followup_task`, `interrupt_agent`, `list_agents`, `send_message`, `wait_agent`)**; then a 19,353-byte developer message ("You are Codex, an agent based on GPT-6 …", the base instructions), a 3,511-byte `<skills_instructions>` block listing a bundled system skill (`imagegen`, from `$CODEX_HOME/skills/.system`, created in the private home), a 2,604-byte `<multi_agent_role>` message ("You can spawn sub-agents … and those sub-agents can spawn their own sub-agents"), a 410-byte `<multi_agent_mode>` message, a 648-byte `<environment_context>` (cwd, shell, date, timezone, the sandbox as a `permission_profile`), and the user message. Request fields: `reasoning {effort: medium, context: all_turns}`, `include: [reasoning.encrypted_content]`, `text.verbosity: low`, `tool_choice: auto`, `parallel_tool_calls: false`, `store: false`, `prompt_cache_key` = the thread id, `client_metadata` with an `installation_id`, session and thread ids.

## 2. What this settles

1. **The app-server is a workable adapter transport.** `initialize` → `initialized` → `thread/start` → `turn/start` → `turn/interrupt` all work over stdio in under a second each; `thread/start` echoes the effective sandbox and approval policy, which the adapter can verify against the pin (the T9 matrix's "capability probing" row). The generated JSON schema is the fixture a Codex adapter pins, as `openapi-2.0.18.min.json` is pinned for OpenCode.
2. **MCP spawn and filtering are first-class and observable.** `mcpServerStatus/list` returns the server's runtime status, `serverInfo` and its tools by name; `enabled_tools` filters that list; a failed server produces an explicit status and a notification with the error text. This is the opposite of OpenCode 2.0.18, where a failed server was silent (`T9-live-probe-1-results.md` V4), and it is what `aew opencode`'s missing check (T1 §14 question 7) should look like on either harness.
3. **Codex 0.160.0 does not expose MCP tools to the model as function tools at all.** They are **deferred**: discoverable only from inside the `exec` JavaScript runtime by filtering `ALL_TOOLS`, at a fixed cost of about 3.6 KB (shared type declarations) however many tools the server has. Neither `enabled_tools` (C2), nor disabling the code-mode host (C5: Code Mode "fails closed" but the request is unchanged), nor the removed `tool_search_always_defer_mcp_tools` flag (C8) changed the request. **[inf]** On this pin the T1 surface would be reachable only through a model writing JavaScript, the same situation OpenCode's Code Mode produced before `codemode: false`; Codex has no per-server equivalent of that switch in the configuration reference, and the feature table lists `tool_search` as removed and `tool_search_always_defer_mcp_tools` as removed-but-true. **[rec]** The matrix row "MCP tool registration" for Codex becomes NEEDS LIVE PROBE on each new pin, and the Codex adapter's first support target should state that typed Lead tools are not reachable as function tools on 0.160.0; `thread/start`'s `DynamicToolSpec` (a `function` with `deferLoading`, or a `namespace`) is the documented alternative for client-registered tools and the obvious next probe (it needs `experimentalApi: true`; the v2 schema has the type but no field named `dynamicTools` on `thread/start`, so where it is passed must be found in the experimental schema).
4. **Sub-agents are on by default and the flags did not turn them off in the request.** The `collaboration` namespace (six tools) and the `<multi_agent_role>` instruction ("sub-agents can spawn their own sub-agents") were present in every variant, including with `--disable multi_agent` and `features.multi_agent = false` in the private config. **[inf]** Either the flag is honoured at call time (a denied `spawn_agent`) rather than in the request, or the setting is `[agents] enabled = false` (the subagents page names it) rather than the feature flag; the probe did not try `[agents] enabled`. **[rec]** For AEW runs this is a DELIBERATELY DO NOT USE that must be *verified in the request* by the "nothing else loaded" conformance scenario, not assumed from a flag; until it is, a Codex run would present the model with uncontrolled recursive delegation tools, exactly what the addendum forbids.
5. **A bundled skill and a 19 KB base prompt ride along.** A fresh private `CODEX_HOME` gets a `.system` skills directory with `imagegen`, advertised in the instructions; the base instructions are Codex's own (replaceable with `baseInstructions` on `thread/start` or `model_instructions_file`). Both are context the AEW launch contract did not ask for; the adapter must set `baseInstructions` and disable system skills (`[[skills.config]] enabled = false`, or `skip_host_skill_discovery` when it leaves "under development").
6. **The sandbox is reported, not only configured:** `thread/start` returns the effective policy and the `<environment_context>` tells the model its `permission_profile` (`file_system type="restricted"`), which is useful telemetry for the run label's second line (T9 §A "native sandbox").
7. **Release engineering facts for T10:** the release ships signed (`.sigstore`) musl tarballs with a bundled `bwrap` and `rg` and a `codex-package.json` layout manifest; it has `codex doctor` and `codex update`; `codex-code-mode-host` is a separate binary the app-server requires for Code Mode. A Codex air-gap bundle is therefore one tarball plus its sigstore bundle.

## 3. Not shown

- No model turn ran; whether a model finds the deferred tools through `ALL_TOOLS` is an evaluation question.
- `DynamicToolSpec` registration was not probed (experimental API; field location unknown from the v2 schema).
- `[agents] enabled = false` and `request_user_input` suppression were not tried.
- The app-server over `unix://` under `--unshare-net` (T6) was not probed.

## 4. Changes to the T9 note

§A rows for Codex: **MCP tool registration** → deferred by default, cost about 3.6 KB fixed, tools reachable only inside `exec`; recommendation NEEDS LIVE PROBE per pin, with `DynamicToolSpec` as the candidate. **Tool filtering** → `enabled_tools` filters the server's inventory (observable) but not the request shape; **subagents** → present in the request despite the flags tried; DO NOT USE until the request proves otherwise. **Capability probing** → `generate-json-schema` works; the v2 schema is the fixture. **Process lifecycle / events** → `mcpServer/startupStatus/updated` is the loud failure signal the Lead-side check needs.
