## Questions from the brief

| Question | Answer |
|---|---|
| Any path that creates an invocation or run without going through the predicate? | None found. Invocations are created only by `Invocations.new_invocation` (`workspace_ops.py:74`), reached from five routes that each call `decide_in` first; runs only by `_record_launch_run` (inside `new_invocation`, under `--launch`) and `harness_launch` (after `decide_in`). Every one of those commits through `lead_txn`, whose finalizers run `Dispatch.finalize`. The enforcement does rest on `lead_txn` being the only commit path for such transactions (see note 1). |
| Can one decision admit more, or other, than what it checked (role, card, scope, unit, count)? | Not for those five attributes: admission requires the same unit, a creating entrypoint, the resolved card's id and hash, the resolved role, the declared or decided scope, and each decision is spent once; a run needs a `harness.launch` decision naming its own invocation. What the decision *checks* can be other than what the Lead recorded: the predicate reads the Ticket record and plan from files whose recorded hashes it does not compare (F1). The invocation's workspace or candidate is not bound by admission (note 2). |
| Can a stale decision be reused after the state changed (no cached ALLOW)? | No for control state: a decision carries the revision it was computed at and `finalize` refuses any other. Policy files are outside control state; a decision records their digests but `finalize` does not compare them (note 3). In the real routes the decision is always computed inside the committing transaction, so this is hardening only. |
| Class 0 eligibility and the non-waivable acceptance-check gate: any bypass? | The gate is sound where it applies: added to the obligations of every mutating gate context, required before review, at COMMIT_READY and at publication, non-waivable, evaluated under the current check definition and snapshot. ## Findings

### F1. Minor — the predicate reads the Ticket record and the accepted plan without checking the hashes control state records for them

- **Where:** `src/aew/engine/assurance_ops.py:46-57` (`_inputs`: `record_meta(unit)` and `read_record(plan["path"])`), `src/aew/engine/evidence_ops.py:86-87` (`record_meta` reads the file), `src/aew/knowledge/records.py:147-150` (`read_record` validates the schema only), while `unit["record_sha256"]` and `unit["plan"]["sha256"]` exist in control state and are compared only by `status` (`status_ops.py:25-32`) and by the `accepted_plan` gate.
- **Guarantee:** m4-ambiguity-report "M4-A as built": Class 0 eligibility is "the Lead's three recorded assertions", a bounded scope and an acceptance check; the amendment §2: "AEW enforces the predicate when Class 0 is requested". The things enforced are the Lead's recorded facts, which control state pins by hash.
- **Scenario:** a Class 0 Ticket created without `--class0-assert` is refused (`CLASS0_ASSERTION_MISSING`). The record file `work/<T>/ticket.md` is edited out of band to add the three assertions. `status` reports "record ... was modified or removed outside AEW"; `dispatch explain` says allowed; `work assign` admits the implementer and records an allowed decision. Likewise a plan whose `affected_paths` name a protected path refuses (`LINT_AFFECTED_PROTECTED`) until the plan file is edited, after which assignment is admitted (the `accepted_plan` gate catches the plan edit later; nothing catches the record edit). Scope, acceptance checks and acceptance inputs come from the same file, so the protected-overlap, hard-trigger and acceptance-check decisions rest on it too. Within the same-UID threat model this is not an authority escalation, but it is the one place where a decision checks something other than what the Lead committed, and the engine already holds the hash to refuse it.
- **Fix:** in `record_meta` (or `_inputs`), compare `sha256_file(record)` with `unit["record_sha256"]`, and the plan file with `plan["sha256"]`, and refuse with `INTEGRITY_ERROR` naming the file; `dispatch explain` then reports the same.
- **Reproduced:** yes, `test_r1_...` (`repro/run-r1-r3.log`). Confidence: high.

### F2. Minor — Class 0 "bounded subject" is a denylist of five literal globs

- **Where:** `src/aew/engine/assurance.py:30` (`CATCH_ALL = {"**", "**/*", "*", "./**", ""}`), `assurance.py:108-112`.
- **Guarantee:** the amendment §2, "a bounded, known subject"; the report §2.3 "a bounded scope matching tracked files".
- **Scenario:** `--scope '**/*.py'` (every Python file in the repository) is not in the list and matches tracked files, so a Class 0 Ticket with it is eligible with no obligation. In the fixture the protected-overlap guard happened to refuse it because `vendor/**` is protected; in a project with no protected paths, or with `**/*.md`, `src/**`, `*/**` or `[a-z]*/**`, it passes. The semantic assertions remain the Lead's, but the structural check is weaker than the text implies.
- **Fix:** replace the denylist with a measure: refuse when the scope matches more than a policy fraction or count of tracked files (for example more than N files or more than a quarter of the tree), or when any scope glob has `**` as its first segment; record the matched file count in the decision's facts so `explain` shows it.
- **Reproduced:** yes, `test_r2_...` (`repro/run-r2.log`). Confidence: high.

### F3. Minor — `--acceptance-check` on a non-mutating Ticket is accepted and never evaluated

- **Where:** `src/aew/engine/work_ops.py:317-319` (refused only for Stories and Epics), `src/aew/engine/gates.py:48-55` (`with_acceptance_checks`), applied only in the mutating gate context (`evidence_ops.py:166`); the non-mutating context (`nonmutating_ops.py:634`, `evaluate_evidence_unit`) never adds the gate.
- **Guarantee:** the report "M4-A as built": "A check the Ticket declares with `--acceptance-check` becomes the `acceptance_checks` gate, on any class". The amendment §9.4 limits Class 0 enforcement to mutating Tickets, but says nothing about silently dropping a declared acceptance check.
- **Scenario:** `work create ticket --non-mutating --acceptance-check unit` succeeds; the record carries `acceptance.checks: [unit]`; `gate show` lists no `acceptance_checks` gate and nothing non-waivable; the Ticket can reach DONE without the check having run. A Lead who declared the check believes it is required.
- **Fix:** either refuse the flag for non-mutating Tickets with a message pointing at §9.4, or add the gate to the non-mutating context (the executor's observation can run the check).
- **Reproduced:** yes, `test_r3_...` (`repro/run-r3.log`). Confidence: high.

## What looks sound

- **One creation point.** `new_invocation` is the only writer of `state["invocations"][...]`; `_record_launch_run` and `harness_launch` are the only run writers. Every route reaches them through `decide_in` inside its own transaction.
- **Commit-time admission** (`dispatch.py:283-337`): new invocations and new runs are matched against unused, allowed decisions from this transaction at this revision; card id and hash, role, scope and unit must agree; one decision admits one invocation; a run needs a `harness.launch` decision for its own invocation; run 1 of `--launch` is attributed to its dispatch's decision. The finalizer runs before archival.
- **Wrapper entrypoints** cannot be decided on their own; the broker relays to the CLI entrypoint it names.
- **Guard order and semantics.** Migrated checks stop at the first refusal with their original codes; the M4 guards all run and report every condition; obligations and blockers must use registered reason codes; guards are side-effect-free (the `_inputs` git read is read-only).
- **Class 0 eligibility** where its inputs are trusted: scope, goal and configured deterministic check, the three assertions, no acceptance input in scope, no review trigger reached, no inherited floor or non-waivable gate, clean lint; refused with every reason, never reclassified; `reclassify` is raise-only, never below an inherited floor, and records a decision. A new implementer and every relaunch of an implementer re-run the eligibility guards.
- **The acceptance-check gate on mutating Tickets:** present in `PRE_REVIEW`, in the COMMIT_READY gate set and in the publication re-check; non-waivable (`evidence_ops.py:949-951`); evaluated under the current check definition and current snapshot.
- **Query equals execution:** `explain` calls the same `decide` on the committed state; the conformance test compares the two and proves a policy change is seen by the next dispatch.

## Process, architecture and efficiency notes (outside the findings)

1. **Enforcement rests on `lead_txn`.** `Dispatch.finalize` runs only through `Kernel.finalizers`, which `lead_txn` and `migrate` call. Other commit paths (`lead_acquire`, `lead_handoff_accept`, `lead_takeover`, the harness request commits) use `store.session()` directly and run no finalizers. None of them creates an invocation today, but the invariant "no invocation without a decision" is enforced by convention at the transaction level, not by the store. Moving the new-invocation check into `Session.commit` (compare `before["invocations"]` with the committed state) would make it structural.
2. **Admission does not bind the workspace.** `_admitting_invocation` checks unit, entrypoint, card, role and scope, but not the workspace or candidate the guards resolved (`facts["workspace"]`, `facts["workspace_id"]`) against `inv["workspace"]`. The routes pass them through faithfully; binding them would close the last attribute a decision checked but admission does not compare.
3. **Policy digests are recorded, not re-verified.** A decision carries `dependency_digests.policy`; `finalize` could compare them with the current policy files so that a decision computed at this revision but before a policy edit in the same revision is refused. Only reachable by internal misuse today.
4. **`CLASS0_PLAN_LINT` fires on warnings.** `class0_blockers` treats any lint entry, warnings included, as disqualifying (`assurance.py:150-153`), so an affected path outside the scope (a warning for Class 1+) refuses Class 0. Reasonable, but the report says "a clean plan lint" without saying warnings count; say so in `aew guide`.
5. **The `assign.kind` guard is the only place `facts["archetype"]` is set for assignment**; the M4 guards key on it. If a future entrypoint grants mutation without setting it, the M4 guards silently do nothing. A registry-level assertion that every entrypoint in `MUTATION`'s audience sets `archetype` would catch that at composition.
6. **Test cost.** The conformance lane drives every entrypoint through the CLI; the dispatch unit, regression and conformance set took 5 minutes (60 tests) here. The unit layer (`test_dispatch_registry_and_commit_check.py`) covers the finalizer well with fakes; an in-process driver for the routes would cut the integration cost.
