## Questions from the brief

| Question | Answer |
|---|---|
| Atomicity across a crash at any point (partial writes, rename ordering, the manifest pin) | Sound. One validated serialization; redo record fsynced before the single `os.replace`; apply after; roll-forward idempotent and conservative; the manifest is a staged write re-pinned in the same state and reloaded under the lock after apply. The crash matrix (8 store points, 3 history points, in-process and real processes) passes here. One wrong result found: a write that was applied long ago and then edited out of band is reported as an interrupted apply and blocks the documented remedy (F1). |
| Concurrent writers: lock correctness on Windows and POSIX, stale-lock handling | Sound in the normal case: every read and write takes the OS lock, recovery runs first, the revision is compared under the lock, the OS releases the lock on death. One gap on POSIX: the lock is identified by path, so unlinking `local/control.lock` under a holder lets a second writer in (F2). Windows refuses the unlink while the handle is open, so it is not exposed. |
| Archive and history: can a verified history accept a forged or reordered entry? | No, within the stated trust boundary (an actor who can rewrite `control.yaml` can forge anything; ADR-0011 says so). Entries are chained over canonical JSON including `seq`; sealed segments are linked by file hash to the root's `sealed_head`; the tail must fold from the sealed boundary exactly to the root; records are read only against the hash their entry pins; the index is a locator whose every answer is re-authenticated. A derived index can at most hide records, which the full audit catches. One availability defect: a busy derived index makes an authoritative commit fail (F3). |

## Findings

### F1. Minor — an out-of-band edit of a file the last transition staged is reported as a transition in progress, on every read, and blocks `manifest adopt`

- **Where:** `src/aew/engine/store.py:361-363` (recovery re-applies the last transition's redo record on every read), `store.py:374-389` (`_load_txn`: any staged path whose hash is not the after-hash is "pending"), `store.py:391-404` (`_apply` fails closed with "modified outside AEW while a transition was being applied"), `src/aew/engine/api.py:132-145` (`manifest_adopt` opens a session, so it runs the same recovery).
- **Guarantee:** ADR-0001 "Roll-forward writes a target only if it is at its recorded before-hash or already at its after-hash. Anything else is an out-of-band edit and fails closed"; ADR-0001 M8 "Pin mismatches are still refused for mutations and reported as contradictions" with `aew manifest adopt` as the remedy.
- **Scenario:** `authority accept` rewrites `project.yaml` as a staged mutable write and the commit applies it. The operator then makes a reviewed manual edit of `project.yaml`, the case `manifest adopt` exists for. Until the next commit, `last_transition.txn` still names that write, so every read (`lead show`, `status`, `resume`, a run supervisor's poll) fails with `INTEGRITY_ERROR: project.yaml was modified outside AEW while a transition was being applied`, which is false: the apply completed. `manifest adopt` fails the same way, so the documented remedy is unreachable; the operator must restore the exact previous bytes by hand (the error gives the two accepted hashes but not the content). The same edit made one commit later yields the intended pin mismatch, and `manifest adopt` resolves it. The same applies to `history/tail.yaml` after any archival commit, where editing is less plausible.
- **Fix:** record that a transition's apply completed, so recovery can tell "unapplied" from "applied, then edited": for example `create_exclusive` a marker `state/txn/<rev>.applied` right after `_apply` (before `after_apply`), and in `_recover` skip the roll-forward when the marker is present. A later mismatch then surfaces through the pin check with the right message. Deleting the redo record instead would make a missing record ambiguous; a marker keeps the fail-closed behaviour for a true crash.
- **Reproduced:** yes, Windows, `test_r1_...` (`repro/run-r1.log`). Confidence: high.

### F2. Minor — on POSIX the control lock is identified by path, so removing the lock file lets a second writer in

- **Where:** `src/aew/engine/lock.py:26-41` (open by path, `flock` on that descriptor; no check that the locked inode is still the path), `store.py:78` (`local/control.lock`, under the directory ADR-0011 calls disposable: "`aew resume` after deleting `.aew/local` remains complete").
- **Guarantee:** ADR-0001 "Every engine operation, read or write, holds an OS advisory lock ... Two concurrent writers cannot lose updates".
- **Scenario:** process 1 holds the lock inside a commit. Someone removes `.aew/local` (an operator following the ADR's own statement that it is disposable, a cleanup script, a test). Process 2 opens `local/control.lock`, creating a new inode, and its `flock` succeeds at once. Both now believe they hold the lock. Process 2 reads revision N while process 1 is replacing N+1; both commit N+1 (each checked its expected revision against its own parse), the second replace overwrites the first, and the first's staged writes may be applied against the second's state. On Windows `os.unlink` of an open handle is refused, so the same action is harmless there.
- **Fix:** after `flock`, compare `os.fstat(fh).st_ino/st_dev` with `os.stat(path)`; on mismatch close and retry. Never remove `local/control.lock` from AEW's own cleanup paths, and say in ADR-0011 that `local/` is disposable only while no AEW process runs.
- **Reproduced:** yes, Rocky 8 (`repro/run-r2-rocky8.log`): with the file in place the second taker is refused after its 3 s timeout; after the unlink it acquires in 0.00 s while the holder still holds. Confidence: high. The lost-update consequence was not driven to completion (no pytest on the VM while it was in use); the lock violation itself is shown.

### F3. Minor — a busy derived index makes an authoritative commit fail

- **Where:** `src/aew/engine/archive_ops.py:632-650` (`_index` syncs the SQLite index inside the transaction when a commit needs a cold fact), `archive_ops.py:646-650` (`_archived_refs` reads `facts_from_cold` for a new edge to archived work), `src/aew/history/index.py:63,82-95` (30 s SQLite timeout, then `LockTimeout`).
- **Guarantee:** ADR-0011 "a SQLite/FTS/other lookup database, if useful, is derived and rebuildable, never authority"; "Loss of a derived index may reduce convenience or performance, never erase the durable knowledge".
- **Scenario:** another process holds a write transaction on `local/history.sqlite` (a long audit's `check()`, a reindex, a stuck reader). The Lead runs `work create ... --depends-on A` where A is archived. The transaction needs A's facts, syncs the index inside the control lock, waits 30 s, and fails with `LOCK_TIMEOUT`. Nothing is lost, but an authoritative commit was refused because of a derived file, and the control lock was held for the whole wait, which is long enough to trip other pollers (a run supervisor ends its run as `crashed` at a 60 s lock timeout).
- **Fix:** when the index is busy, fall back to walking the manifest for the one fact needed (the history is authoritative and readable without the index), or sync the index outside the control lock before the transaction starts.
- **Reproduced:** yes, Windows, `test_r3_...` (`repro/run-r1-r3.log`): `LOCK_TIMEOUT` after 31 s. Confidence: high.

## What looks sound

- **Commit ordering.** Validate and serialize before any disk write; stage the redo record (temp, fsync, replace, directory fsync on POSIX); write the control temp with fsync; one `os.replace`; apply; manifest refresh; log and views. A crash at any of the eight store points and three history points exposes revision N or N+1 (crash matrix passes here, in process and with real processes killed by `os._exit`).
- **Checksum trailer** fails closed on truncation and edits; the parse cache is keyed by the exact bytes and never handed out.
- **Redo staging.** Writes are applied only after the commit point; roll-forward is idempotent (already-at-after skipped) and conservative (any other content fails closed); staged records newer than the committed revision are discarded; spent records are removed only after the current one is fully applied; a missing redo record with unapplied writes is an integrity error, not silently skipped.
- **Immutable records.** `create_exclusive` (link-and-unlink on POSIX, rename on Windows) and the commit's immutable check refuse overwrites; prewritten records must hold their declared hash at commit and are listed in the redo record by hash only.
- **Compare-and-swap.** The expected revision is checked against the state parsed under the lock, inside the lock, in every session.
- **Manifest pin.** Rewritten as a staged write and re-pinned in the same state; reloaded under the lock after apply and after recovery; revalidated by file identity outside a session.
- **Lock semantics.** `flock` and `msvcrt.locking` are released on process death; nesting from the same process blocks rather than re-enters; the 60 s timeout surfaces as `LockTimeout`.
- **History chain.** Hash over canonical JSON (no floats, no non-JSON types, timestamps quoted by the dumper and so round-trip as strings); `seq` inside the hash and checked by `fold`; sealed segments exactly 256 entries, immutable, linked by file hash through every later segment to the root's `sealed_head`; the tail must start at the sealed boundary and fold exactly to `{count, head_h}`; an earlier verified point must be on the chain.
- **Records** are read only against the hash their entry pins; bundles pin their unit record, plans, evidence, cited checks and completion record, and evidence pins its logs; the full audit walks all of it.
- **Index as locator.** Every query result is authenticated entry by entry against the root-pinned history and against the query's own predicate; a mismatch rebuilds once and then fails; completeness is checked at sync; an index ahead of the root is bounded by `seq <= upto`; a busy index is never mistaken for damage.
- **Audit (R2).** Root and tail bytes copied together under the lock, verification outside, recorded only if the root is still current, otherwise continued incrementally; the audit entry is checked locally before the verified root advances; the audit never claims to have audited itself.
- **Migration.** One transaction; bundles prewritten and referenced by hash; interrupted migrations leave only unreferenced records, removed on retry; refused while any run may be live.

## Process, architecture and efficiency notes (outside the findings)

1. **Temp-file cleanup covers four directories only** (`store.py:430-439`): `.aew`, `state`, `state/txn`, `state/log`. A crash inside `atomic_write` elsewhere (`work/<id>/`, `history/`, `evidence/`) leaves `.name.XXXX.tmp` files for ever. Harmless, but `aew doctor` could list them.
2. **Windows durability.** `fsync_dir` is a no-op on Windows (`util.py:150-152`), so a rename is durable only as NTFS journaling makes it; after a power cut the file can be the previous revision, never a hybrid. Worth one sentence in ADR-0001's limits next to the NFS note.
3. **Index rebuild inside the lock.** `_index` (`archive_ops.py:632-650`) can trigger a full rebuild of the SQLite index inside a Lead transaction; on a long history that holds the control lock for the rebuild. Related to F3: do index maintenance before taking the lock.
4. **`_rows` rebuild path on Windows.** `HistoryIndex._rebuild` unlinks the database (`index.py:97-101`); with another process holding it open this raises `PermissionError`, which `_rows` does not catch, so a corrupt index plus a concurrent reader surfaces as a Python traceback rather than an AEW error.
5. **Reads write.** `store.read()` renders views and may write a log file on every call (`store.py:364-366`). Correct under the lock, but a read-only credential still needs write access to `.aew/state`, and it costs a render per read.
6. **Policy files are not pinned.** Outside this area but adjacent to the manifest pin: `gates.yaml` and `guardrails.yaml` are read fresh on each use and are not hashed into control state (the execution policy and check definitions are). An edit changes obligations silently; the manifest pin does not cover them.
7. **Audit backlog of one.** When a Lead credential ends in the same commit as an audit, the audit's verified root is one entry short of the commit's root by design. Fine, but `status` will show a backlog of 1 until the next audit; a note in the audit output would avoid a puzzled operator.
8. **Test cost.** `test_store_processes` spawns a real process per fault point and is lane `serial`; the whole store, history and archival set took 10 minutes (106 tests) here. Reasonable for what it proves.
