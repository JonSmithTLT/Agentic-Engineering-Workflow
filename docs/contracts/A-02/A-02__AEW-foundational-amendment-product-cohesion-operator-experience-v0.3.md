# AEW Foundational Amendment — Product Cohesion and Operator Experience v0.3

Operator endorsed the design direction, not the exact normative text. v0.3 incorporates two independent reviews of v0.2, particularly the prevention of implementer-defined scope exclusions and the preservation of operator-action reachability during staged delivery.

**Authority:** Proposed additive foundational obligations. This document does not amend the adopted Foundational Requirements v0.4, Engineering Workflow Umbrella v0.4, Authority/Delegation/Classification v0.3.1, Hosting/Execution v0.3.1, or Assurance/Evidence v0.3.1 until the operator explicitly adopts the amendment. **Identifiers:** `PC-FR-*` and `OI-FR-*` are **amendment-local stable identifiers** pending reconciliation with canonical `AEW-FR-*` numbering. ## 1. Product purpose and architectural boundary

AEW is a composed engineering orchestration platform, not a collection of self-contained features later joined by implementation archaeology. The requirements-driven architecture must identify the capabilities that *need* to cooperate to fulfill an intended engineering or operator outcome, establish their contractual information and authority relationships, and leave implementation strategy replaceable. Isolated component correctness is not sufficient proof of intended composed behavior. Conversely, integration is not a reason to collapse intentionally independent reviewers, trust zones, decisions, or low-cost standalone utilities.

The **supported API and website are first-class product surfaces** wherever the intended operator experience depends on them. The domain contract decides the meaning and authority of facts and operations; the supported API contract specifies which relevant facts, events, and authorized actions its consumers can rely on; and the website/operator-interface contract specifies usable journeys that consume those interfaces. Neither API nor website invents canonical state, authorization, or assurance conclusions. Operator-authorized staged delivery is legitimate; silently treating backend completion as an operator-journey PASS is not. A capability active now that requires operator decision/action must have a supported operator path **now**, even when its future website journey is deferred.

**Normative allocation rule:** Accepted objectives, authority-confirmed scope and operator-authorized release commitments determine what is applicable; implementers cannot narrow those obligations by omitting a consumer. Foundation establishes the *required outcome*; umbrella/domain contracts establish the *producer–consumer behavior*; the API contract establishes the *supported interface and consumer guarantees*; the site/operator contract establishes the *operator journey*; implementation designs choose physical mechanisms; Assurance qualifies observed delivery. Existing adopted contracts remain the owners of authority, execution, and verification decisions.

### OI-FR — First-class operator API and website experience

| ID | Proposed guarantee | Illustrative disconfirmation witness |
|---|---|---|
| `OI-FR-01` | AEW shall support operator-facing journeys committed in the operator-authorized release or milestone scope through usable API and website experiences where those surfaces are committed, while preserving independently supported operator interfaces and valid staged delivery. | Operator action requests exist in canonical state but the committed website journey offers no way to see or reach them. |
| `OI-FR-02` | For each operator-facing journey whose authorized delivery scope includes the supported API, AEW shall provide a contracted path from the governing domain fact or action owner through that API to its intended consumer/action, and shall qualify the composed behavior before claiming the API-backed journey delivered. Independently supported local or outage-read journeys need not route through the API or website. | A visible control calls a demonstration-only mock with no supported server operation, but the production feature is called ready. |
| `OI-FR-03` | Operator-facing representations shall distinguish current, stale, unavailable, unsupported and historical information as relevant to the task, with usable navigation or an explicit unavailable destination for consequential subjects. | A revoked Lead appears active from an old cache, or a high-priority request has no accessible destination. |
| `OI-FR-04` | API and website interfaces shall preserve canonical identity, vocabulary, decision authority and permitted actions from their governing domains and shall not create competing lifecycle, execution, classification, or assurance authority. | Site code independently marks a Ticket verified, or restores a revoked grant because the last cached result was PASS. |
| `OI-FR-05` | AEW shall make material intended interface-consumer coverage and deliberate non-exposure ascertainable, so missing projections, incompatible values, unhandled consequential events/actions or unusable links can be identified without a second authoritative registry. | A new actionable event kind is emitted by the engine but cannot be projected or navigated by its intended operator consumer and the omission remains invisible. |
| `OI-FR-06` | AEW shall distinguish engine capability, contracted API capability, usable website capability and qualified end-to-end operator journeys for release/acceptance claims. Applicable journeys and permitted staging shall be determined by recorded operator-authorized release or milestone commitments, not unilaterally narrowed by an implementer, and no partial delivery shall imply unearned product completeness. | Backend logic is finished and a website is planned for a later authorized milestone, but the present milestone is described as fully usable through the site. |
| `OI-FR-07` | AEW’s supported API shall provide its authorized, declared consumers the domain-derived information, events and authorized actions required by their committed use cases, with appropriate identity, meaning, authorization, freshness/ordering, intentional omission and failure guarantees, without requiring exposure of every internal datum or any particular protocol. | Assurance publishes ordered determinations internally, but the API exposes an undifferentiated `passed=true` field that permits a delayed old PASS to mask a current HOLD. |
| `OI-FR-08` | Any capability active in a release that can require an operator decision or action shall provide, in that release, at least one supported authorized interface through which the operator can discover the pending need and submit an authorized response under supported operating conditions. Temporary unavailability or denial shall be truthful and actionable; staging the website or API shall not eliminate the required operator path. | A required adjudication or close disposition awaits the operator, but every supported surface is deferred and the operator cannot discover or respond to the request. |

## 3. Native composition allocation — known relationships to preserve downstream

This table illustrates **contract handoffs**, not adopted details of future domain contracts, implementation data models, or extra authority owners. Future designers shall trace the governing sources and decide applicability. A producer's obligations do not by themselves certify consumer behavior.

| Composed outcome | Canonical producer/owner | Required consumer question | Boundary that must specify the interface |
|---|---|---|---|
| Verified work advances or returns for correction | Assurance owns attributable determinations; Authority governs who may decide and act | Coordination must know the affected package/obligation, current versus historical determination, holds, and safe progression when currentness is unknown | Work Identity for stable subjects; Coordination for ordered consumption and transitions; API/site for truthful projection |
| Authorized engineering learns from prior findings | Assurance provides qualified findings; Knowledge governs admission and retrieval | Which findings are admissible, relevant and accessible without transferring prior conclusions as proof? | Knowledge boundary with Assurance/Work Identity consumer guarantees |
| Operator sees why work is waiting and can respond | Coordination/Authority own state and decision rights | Which actionable facts, subjects and authorized actions must be exposed, with freshness and failure meaning? | Supported API and operator website contracts |
| Lead restarts or closes a hosted generation | Hosting/Authority own lifecycle and grants | How does a user see current vs stale generation, held results and permitted operator actions without UI-local grant logic? | Hosting/Authority semantics consumed by Coordination and API/site |
| Compatible dependent work integrates | Work Identity identifies packages/revisions; Coordination owns applicable dependency/integration disposition | Which interface commitments and qualified upstream conditions may downstream work rely on? | Work Identity, then Coordination/Integration contracts |

**Explicit freshness handoff:** A same-package qualified PASS can later be undermined by a credible contradiction. Assurance retains the authentic historical PASS and a newer attributable determination/hold. Coordination must define currentness and prevent a delayed older PASS from restoring completion/release authority. The API and site must truthfully project current versus historical assurance, including unknown-currentness states, without becoming assurance authorities. No cursor transport, database, cache, or event bus is prescribed here.

## 4. Intentional exclusions and safeguards

- **No universal coupling:** Composition is required for *materially intended* shared outcomes, not every relationship that could theoretically be useful. Other supported interface clients, including CLI and automation, remain legitimate.
- **No duplicate normative state machine:** Required coverage may be calculated from adopted contracts, accepted capability scope, canonical event/value definitions, and consumer implementations. Any coverage index remains a derived navigation/evidence aid, not a second source of approval, state or authorization.
- **No retroactive requirements promotion:** Existing code, frozen historical designs, API routes and UI mockups are evidence or candidates; they do not become normative just because they exist, pass tests, or carry a historic approval/freeze label.
- **No default exposure:** A first-class API does not mean every secret, protected record, operational detail, or internal event is exposed. Exposure is justified by supported consumer needs and all adopted authority, hosting, privacy and evidence restrictions.
- **Admission-time ownership, not implementer opt-out:** Material composed outcomes and affected producer–consumer duties are derived from accepted objectives and governing requirements at admission or planning, consistent with `AEV-01.a`. Required plan assessment challenges missing dependencies under `EW-U04.c`. The implementing party may identify additional relationships, not unilaterally delete mandatory ones.
- **Legitimate later discoveries:** New qualified knowledge may reveal previously unknown consumer relationships. Reassess affected allocations and authorization through existing `EW-U09` / `ADC-02.d` mechanisms before implementing the new relationship; preserve unaffected work and do not force a complete restart.
- **No forced simultaneous release:** Operator-authorized release/milestone commitments, not an implementer’s assertion, determine in-scope operator journeys. The claim must match what was actually promised and delivered at that stage. A backend-first release may stage a website but cannot strand an active mandatory operator decision.
- **Supported non-web and outage paths:** A supported local CLI or other authorized direct-read path need not depend on the supported API, live Lead, inference gateway, main orchestration service, or website merely to qualify its own journey. Preserve adopted `AEW-FR-30.a` and `AEW-FR-30.b` outage-read duties and their authorization/secret protections.
- **No weakening of independence:** Reviewers do not implement their own corrections; consumers cannot create their own assurance conclusion; an API/site does not authorize mutations forbidden by the governing owner.
- **Contract-first substitutability:** An independent component team can implement a conforming producer or consumer using the behavioral semantics and requirements relationships without reverse-engineering historic code or interpreting undocumented informal handshakes.

## 6. Review and allocation questions

1. Is `PC-FR-03` strong enough to require acceptance-derived composition allocation **before affected responsibilities are implemented**, with omission challenged at required plan assessment, without extra paperwork for a trivial Ticket?
2. Does `PC-FR-06` sufficiently define what independent producers and consumers need to know while leaving wire formats and mechanisms to implementation designs?
3. Does `OI-FR-07` establish a first-class API product obligation while `OI-FR-02` and `OI-FR-08` preserve non-web/outage paths and operator decision reachability?
4. Is canonical ownership preserved across Assurance → Coordination → API/site, particularly when historical PASS and newer HOLD are delivered out of order?
5. Can operator-authorized staged delivery coexist with mandatory reachability for operator decisions activated in the same release, without an integration-everything bureaucracy?
6. Can the October 12 historical audit failure classes (missing projections, mock-only routes, vocabulary mismatch, missing destinations and stale reads) be falsified by the scenario set without silently imposing historic design mechanisms?
7. Does the amendment fit **below** the adopted Foundational v0.4 baseline as an additive amendment, without requiring automatic edits to the five adopted contracts?

These are deliberate future boundaries, not implementation tasks assigned by this amendment.

## 8. Designer disposition — recommendation, not adoption

1. **ACCEPT** the two reviewers’ common correction: implementer-authored composition omissions and implementer-defined release exclusions cannot limit obligations derived from accepted requirements and operator-authorized scope.
2. **CLARIFY** `PC-FR-03` allocation before affected responsibilities are implemented, with existing plan assessment and late-discovery change paths; preserve independently useful work.
3. **STRENGTHEN** `PC-FR-02` as a canonical-ownership outcome, `OI-FR-07` as an API product obligation, and `OI-FR-02` for only API-committed journeys; explicitly protect non-web outage reads.
4. **ADD** `OI-FR-08`: every active operator-decision dependency needs a discoverable and usable authorized path in the active release, even when the website is staged.
5. **PRESERVE** implementation independence, proportionate low-overhead work, distinct authority owners, deliberate non-exposure, and valid staging.
6. **RECOMMEND** v0.3 for operator adoption consideration after independent reviewers validate these bounded corrections; do not claim operator adoption or implementation conformance from this document.
