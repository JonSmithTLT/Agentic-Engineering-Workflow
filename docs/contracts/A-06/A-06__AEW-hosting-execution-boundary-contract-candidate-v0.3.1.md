# AEW Hosting and Execution Boundary Contract — Candidate v0.3.1

**Status:** Principal-designer proposal; **NOT OPERATOR-ADOPTED**  
**Date:** 2026-10-15 (focused post-review amendment)  
**Contract role:** Implementation-independent domain/boundary contract governing host custody, execution-effect isolation, and the usable agent execution environment.  
**Baseline authority:** Operator-adopted AEW Foundational Requirements v0.4, Engineering Workflow Umbrella v0.4, and Authority, Delegation, and Classification v0.3.1.  
**Conformance status:** **Unknown / not demonstrated.** Document trace checks and proposed adversarial scenarios are not implementation evidence.

## 1. Purpose and boundary

AEW must furnish a stable, fully equipped, low-friction environment for agents to perform authorized engineering while preventing agent-controlled processes from exercising effects outside their grants. The Lead may remain conversationally persistent and implement small tasks directly, but persistent context does not imply persistent write privilege. A protected supervisor (or equivalent trust boundary) owns grants, canonical records, lifecycle control, containment admission, process custody, and effect admission. An execution context has independently bounded effective permissions for the assignment, including shell/native/harness tools, ordinary subprocesses, background jobs, and remote resources.

### 1.1 Contract precedence and scope

This contract is subordinate to the three adopted baselines. In the event of conflict, the responsible requirements authority must resolve the conflict; a later contract draft does not silently override adoption. F18 v0.6, Q12 and related older designs are **historical adopted operational decisions/design evidence** whose currently effective safety controls remain active until safely superseded, but do not independently define the newly rebaselined normative architecture. This draft preserves their current operative controls where compatible and pins their exact lifecycle source sections in §3.3.

**Operator-directed external/manual development is outside AEW-protected execution.** It may produce untrusted artifacts that later enter the normal admission process, but is neither a supported mutable profile nor a waiver of `ADC-04.n`/`HEB-02.i`. The operator must explicitly select and oversee it; an attached Lead cannot treat failure to qualify as permission to invoke external unrestricted tools. This is not the same event as the Q12 *release-to-manual* lifecycle disposition, although the resulting external contributions have similarly limited trust. Existing protected-state and credential boundaries remain effective. **This contractual distinction does not lift an existing project implementation hold, create authority to run external tools, or certify the security of an operator-owned external development environment.**

The software-research, experimental PoC, unattended-mission, and capability-ToC amendment (`AEW-foundational-amendment-research-experimentation-unattended-v0.1.md`) is **not adopted**. Candidate extension behaviors in this draft are evaluated as prospective compatibility, not as already effective authority. Existing applicable protection rules apply regardless of work type.

### 1.2 What this contract does not define

It does **not** mandate a sandbox product, container runtime, Unix UID count, filesystem arrangement, gateway protocol, Git strategy, new Ticket hierarchy, agent scheduler, model roster, risk class taxonomy, test acceptance criteria, database implementation, or evidence-admission algorithm. It **does** state minimum observable effect-denial classes, enforced principal separation, and trustworthy execution boundaries; implementation designs choose the mechanism. It does **not** declare all scripts safe, all databases disposable, all native harness capabilities preventable, or anything implementation-conformant. The adopted authority and assurance boundaries continue to decide which effects are permitted and what results count as proof.

### 1.3 Normative terms

- **Supervisor:** The protected, non-agent-governed authority/control service or equivalent functional boundary; not a model personality.
- **Lead host:** Long-lived interactive harness/model environment. Its conversation may outlive AEW attachment; it is still model-controlled and not intrinsically trusted.
- **Execution context:** Enforced combination of actor, current grant, assignment, accessible resources, permissible effects, process custody and resource limits. It may reuse infrastructure but not stale authority.
- **Read/inspection context:** Qualified low-effect access for source investigation, explanations and bounded diagnostic activity. Diagnostic commands may have limited writes; “read-only user request” is not proof the invoked tool is read-only.
- **Agent-controlled executable content:** Any script, hook, plugin, build rule, test fixture, import or configuration writable by an agent and then executed or interpreted by any process; its effects remain untrusted even when launched by a verifier or supervisor.
- **Source-mutating agent:** Any model-controlled actor with authority to change governed project code/artifacts, including a directly implementing Lead.
- **Effect path:** Any route available to an actor that can cause consequential effects, mediated or unmediated; includes shell, native harness tools, indirect process/network routes, IPC, files and external services.
- **Custodian / drain:** The previously adopted, supervisor-bounded continuation of an eligible admitted invocation after attachment end; not renewed Lead authority.
- **Admitted result:** Result allowed into a specified downstream use under the governing assurance/authority rules, not simply a process that completed.

## 3. Required contract interfaces, minimum isolation, and open parameters

### 3.1 Decision authority and enforcement boundary

The protected authority boundary establishes current grants; hosting enforces actual effect paths, including unmediated shell, native harness tools, implicit execution through agent-writable project content, provider gateways, IPC, file aliases, and external services. A persistent Lead *conversation* is not a requirement for a persistent unconfined operating-system process. A conforming design might route all project-mutating tools through confined contexts while the Lead base process remains read-only, or rehost the Lead in an appropriately isolated context and recover its conversation on switching. Neither pattern is prescribed or presumed supported. A rehosted credential-bearing harness is **not qualified** if its mutable subprocesses can obtain provider credentials or any privileged effect path without an independent control. The brokered pattern is likewise **not qualified** if any native shell/edit, plugin, MCP server, or inherited subprocess effect bypasses confinement. A native tool absent from a model schema or dispatch registry demonstrates only that specific dispatch behavior, not the integrity of the rule source or OS containment. Agent-controlled workspace configuration—including project-local settings discovered at harness startup or resumption—is untrusted for permission expansion; non-authority-bearing settings can still be consumed through protected validation or bounded projection. This applies to Lead and worker harnesses alike.

The Lead base identity must itself enforce its nonmutating scope; it must not inherit the operator’s privileged account or credentials. A separate workspace directory or Git worktree is not an OS boundary. Where the operator chooses external/manual development, its security and provenance must not be mistaken for a protected AEW execution grant. That choice does not reenable a failed mutable activation or permit ordinary AEW work to bypass the supervisor. In concurrent contexts, indistinguishable security principals must not be trusted to separate grants merely by labels. Ordinary access to read-only project context is permitted, but actual diagnostic commands that produce effects run in an appropriate confined diagnostic profile.

### 3.2 Execution and verification fidelity

A successful process launch/exit is not evidence of contractual verification by itself. Test evidence should identify its material subject and observations. Recording source-state content identities at start and end is a low-cost way to detect changed inputs; unchanged identities support *source stability* but do not independently establish unchanged external inputs, test validity, or assurance PASS. Changed/unknown source identity means the result remains qualified diagnostic evidence unless an applicable verifier independently establishes its suitability. A full immutable repository copy is not mandated for each exploratory test.

A privileged verifier, integration process, or supervisor must not execute agent-authored Makefiles, test plugins, Git hooks, or build steps with its own protected authority merely because it initiated the command. Treat repository-local and repository-directed Git execution policy (including hooks, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, filters, textconv, credential helpers, and conditional configuration includes) as untrusted input whenever an agent can affect it. Untrusted build/test execution takes place in an appropriately confined actor, and the trusted recorder admits evidence from bounded outputs and observations.

### 3.3 Existing lifecycle compatibility and source-specific disposition

This table preserves currently effective F18/Q12 obligations and reconciles them with adopted `ADC-02.f/j`; it does not give a new model actor lifecycle powers. `Q12 §13` means the appended child-disposition decision (including the later operator clarification), not the earlier session discussion. `F18 v0.6 §§10–14` governs operator-controlled close, custody, deadlines, held results, and reconcile semantics. Trust-revocation is an authority-destroying safety event and is not an ordinary detach.

| Operator `aew close`, **no disposition choice** | Same as ordinary detach; absence of choice does not itself revoke trusted child authority | **Eligible drain is default**, subject to custody and limits; close presents active jobs for acknowledgement when operator terminal exists | Held for current authority | Bounded drain and ordinary reconciliation | Q12 §13 pt 1; F18 v0.6 §11.1, §12–13 |

Hard drain deadline is a stop condition; a separate attention/orphan timeout is not. Grant revocation does not magically reverse external side effects.

### 3.4 Minimum isolation profile — normative denial classes

**This is the adopted-Authority-contract dependency made concrete for this Hosting *candidate*.** A deployment may not claim protected mutable conformance until each class is tested from the actual Lead or worker identity, including direct/native and indirect executable paths. A profile can refuse certain capabilities (e.g., real-provider inference inside a mutable sandbox) instead of trying to distinguish intent with unverifiable prompts. The classes are implementation-independent observable outcomes, not a prescription for Linux tools.

| Class | Denial or limitation required | Primary atoms |
|---|---|---|
| C1 — Workspace write boundary | Deny writes outside granted assignment scope and explicitly declared scratch; also deny alias/symlink and other-worktree paths | `HEB-02.c`, `HEB-03.b` |
| C2 — Protected/secret reads | Deny reads of operator credentials, supervisor authoritative state/secrets, and other contexts’ private materials, while permitting explicitly scoped safe read-only project projections | `HEB-01.a`, `HEB-03.j` |
| C3 — Inference/delegation boundary | Default-deny unapproved provider reachability and credentials; permitted agent-software tests must use a profile where inference cannot create unauthorized effectful assignments | `HEB-03.c`, `HEB-03.k`, `HEB-03.n`, `HEB-03.q`, `HEB-01.i` |
| C4 — Network and external effects | Default-deny egress beyond named grant destinations (including local sockets/IPC that route externally); qualify authorized shared-service effects separately | `HEB-03.k`, `HEB-05.d`, `HEB-10.d` |
| C5 — Process and IPC boundary | Deny signals, tracing, interprocess access and supervisor/peer IPC outside grants; protect background jobs across assignment switches | `HEB-03.f`, `HEB-03.l`, `HEB-03.m` |
| C6 — Agent-written execution/content boundary | Untrusted agent-controlled code, hooks, build rules and tests cannot run under privileged verifier/supervisor rights; protected evidence only recorded by separate trusted admission | `HEB-02.g`, `HEB-03.i`, `HEB-03.p`, `HEB-03.h` |

These denial classes must be qualified on the profile actually deployed; passing them on one harness version is not transferable. The Lead base inspection environment must be enforced as nonmutating rather than treated as a prompt label. Missing class qualification refuses the *affected* mutable capability rather than all unrelated safely qualified operations.

### 3.6 Evidence and operational feasibility interface

Before declaring a mutable deployment supported, require valid negative isolation tests *from the actual confined identities*, protected configuration/executable/runtime integrity (including workspace-local capability settings and environment-controlled loading), a tested native harness/MCP route, proven profile-change fencing and qualified positive controls, plus legitimate execution examples: ordinary shell/pytest, restricted model-SDK testing where explicitly authorized, direct Lead fix, switching dirty worktrees, background tests, closing/resuming and qualified result recording. Evaluate both real repository size and acceptable latency relative to authority-approved feasibility thresholds; a profile missing the target is not entitled to silently select an unconfined fallback.

## 5. Conformance evidence required from the Development Lead

Conformance evidence may be collected incrementally by profile and effect class. A narrow dispatch-path result may qualify that path alone; it shall not be generalized to a native shell, protected tool policy, OS containment, provider credentials, or overall C1–C6. An execution profile that lacks a qualified minimum class remains unsupported for affected mutable activation; architectural adoption is distinct from deployment readiness.

Provide the actual supported Rocky 8/other OS and harness versions and hashes, effective security principals, process graph, protected gateway/credential custody, and every reachable effect path. Execute the C1–C6 negative probes from the *real* Lead and worker contexts. Include native shell/edit/subagent, model SDK and provider routes, unknown script, controlled hooks and Git executable configuration (including filters, fsmonitor, credential helpers and includes), protected executable/config/runtime integrity and agent-writable workspace configuration at launch and relaunch, caches, /tmp, symlinks, process/IPC and cross-workspace writes, external test services, launch-time and changed-profile requalification, ordinary close/default drain/trust-revocation differences, and positive normal-task timings at representative repo scale. Preserve command outcomes and environment conditions, not just PASS assertions.

**The contract does not itself demonstrate deployment conformance.** A separate operator-run T1 test on the pinned OpenCode 2.0.18 configuration supports only a denied native `write` dispatch-path claim; see the separately pinned evidence record. It did not establish protected configuration/binary integrity, shell/MCP confinement, or C1–C6. **No full mutable profile or lifecycle conformance is demonstrated.** An unverified tool toggle, plausible OS mechanism, or source diff admission check is not proof of effect prevention. A failed negative probe means the specific mutable profile must remain inactive until fixed and requalified.

## 6. Review focus and unresolved implications

1. **Live hosting feasibility remains empirical.** The actual configured harness must demonstrate all native editing, shell, MCP/tool-server and subprocess effect routes are confined or denied, and that agent identities cannot modify the configuration/binary enforcing this. Neither brokered nor rehosted Lead pattern is assumed supported.
2. **Worktree metadata and hooks are first-order code execution surfaces.** Protected Git/integration components shall handle agent-writable repositories as untrusted data. Do not elevate project-controlled hooks, filters, helpers, includes or build/test plugins through their process identity.
3. **Inference SDK ambiguity cannot be solved by process names.** If genuine agent software must call a model endpoint, isolate/test it under bounded effects. If the profile cannot ensure agentic delegation is not effective, deny that profile combination.
4. **Lifecycle rule must remain exact.** Routine close defaults to eligible bounded drain; compromise/trust revocation stops affected descendants, with separately valid independent authority only as authorized exception.
5. **Usability is an acceptance concern.** Qualification must consider repository scale and agreed feasibility targets, while never trading away containment.
6. **Proposed research tooling is not adopted via Hosting.** Keep prospective features appropriately labeled until their foundational amendment is adopted.
