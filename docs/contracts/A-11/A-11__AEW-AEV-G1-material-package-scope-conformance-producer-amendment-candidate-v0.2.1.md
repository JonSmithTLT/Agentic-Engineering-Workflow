# AEW — AEV Material Package-to-Accepted-Scope Conformance Producer Amendment — Candidate v0.2.1

**Date:** 2026-10-16  
**Revision:** v0.2.1 — bounded v0.2 clarification of initial baseline authority, effective protection/exception semantics; 17 clause identities retained; nonnormative challenges G1-X20–X22 added.  
**Architectural decision:** D-02; addresses the semantic producer allocation behind activation gate G1 / IM-G01  
**Governing sources:** Operator-adopted AEV v0.3.1, CNI v0.2.2, WIS v0.2.1, ADC v0.3.1, HEB v0.3.1 and AOI v0.2.2 (unaltered and hash-pinned in reviewer pack)  
**Scope:** One independent, substitutable AEV qualification function; no new database, work owner, approval registry, scheduler, test runner, or promotion service.

## 1. Why this amendment is necessary

Adopted `CNI-04.d` already prohibits treating agent/peer narrative as accepted scope and requires a **qualified AEV assessment of actual material package changes** using WIS evidence at consequential package acceptance/progression. Adopted `WIS-04.a/e` requires exact material input closure corroborated independently of producer declarations. `AEV-01`, `AEV-05`, and `AEV-06` govern the assurance basis, evidence, and change assessment. **The gap is not the absence of a prohibition:** it is that the current AEV contract does not explicitly allocate an independently implementable, falsifiable *package-to-scope assessment producer*, its positive/negative result basis, and its consumer handoff.

A correct implementation must be able to answer for a particular consequential package: *Which material changes were actually introduced, and which exact accepted revision/authorized scope change permits each one?* A green functional test, a write grant, a peer suggestion, or the producer's change manifest is not by itself that answer.

This amendment **does not** replace or rewrite any adopted contract. On separate operator adoption, it would add the following qualified producer duties to the AEV domain while retaining the currently pinned AEV v0.3.1 bytes. This candidate is not evidence that the capability has been implemented or G1 qualified.

## 2. Boundary and authority allocation

| Boundary | Remains authoritative for | Shall not be inferred |
|---|---|---|
| Accepted requirements / ADC | Which work scope, revisions and material changes are authorized; classification, eligible assessors and required independence | An AEV assessor may expand an objective or grant |
| WIS / qualified package observation | Accepted revision identity, immutable package/delta identity, relevant material integrated input/dependency/condition closure | A self-authored manifest alone proves complete material change coverage |
| **AEV G1 assessment producer (this amendment)** | Qualifying whether the *observed material changes in an identified package* are attributable to the accepted revision, derived obligations or separately authorized changes; proof, exceptions, uncertainties and source-bound determination | An agent assertion or generic test PASS establishes in-scope change |
| CNI / HEB mediated effect boundary | Progression/composition conditions and protected effect-time admission/accepted-input resolution | The AEV assessment is a grant, a promotion action or operator consent |
| API / website | Authorized read projections and source/currentness disclosure | UI computes PASS, waives this check or certifies a stale package |

**Terminology.** *Observed material change set* means the qualified **cumulative** changes from the owner-resolved last protected accepted-input state governing the target (or an operator-accepted and protected initial as-built scope baseline when no qualifying accepted-input starting point exists) to the exact offered package, including materially affected generated output, integrated dependency, behavior, configuration, effective check inputs or composition, under stated conditions. The package submitter cannot nominate a provisional ancestor as the comparator. Identifying protected accepted-input bytes is necessary but **not sufficient** to qualify inherited scope conformance: the baseline's applicable prior assurance pedigree, unresolved findings, limitations and applicability must be qualified or inherited relevant material must be directly assessed. When a pre-G1 accepted state exists without G1 pedigree, its protected accepted bytes remain the comparison base; a dated, exact-byte, scoped as-built baseline acceptance by the competent operator may establish explicit inherited **scope** for bounded subsequent change assessment, but does not retroactively assert a G1 PASS, technical correctness, or waiver of operational protections. Such a baseline is not established by a Lead, worker, repository file, or historical attendance at an approval. *Scope-conformance determination* means an AEV-owned, evidence-qualified obligation-level result for that set and accepted scope; it is **not** technical correctness, generic Ticket completion, protected admission or acceptance of a changed requirement. *Qualified closure* means sufficient coverage of relevant material inputs/changes **and applicable scope/constraint/authorization sets** for the claimed assessment, with explicit exclusions and limits, not a universal whole-repository snapshot. A *protected mechanical assessment* derives its decisive evidence and rule applicability from authenticated, implementer-uncontrolled observation; an implementer-origin self-check is labeled as such and does not become a protected G1 verdict merely by submission.

## 4. Producer/consumer contract: minimum independently implementable behavior

### 4.1 Producer inputs and positive path

The governing accepted-input owner resolves the protected accepted base independent of the submitter, and WIS qualifies its exact identity and the offered package's **cumulative** change/closure. Where that accepted base predates G1, **the competent operator may separately accept its exact bytes as a dated, bounded inherited as-built scope starting point**, recording covered material, exclusions, unresolved adverse evidence and effective security obligations; if no accepted base exists, the operator must explicitly establish the protected initial base. This is a **scope acceptance**, not an AEV assessment, blanket inherited conformity finding, new authority to waive operational controls, or retroactive PASS. The implementing lineage cannot make this decision. AEV qualifies that scope acceptance's applicability and limitations, earlier applicable scope-assurance pedigree where available, and any relevant inherited material not covered by an accepted baseline; the latter requires direct qualified assessment or the affected positive remains NOT_ESTABLISHED. Thus a protected Git ref proves identity, not scope pedigree, while explicit bounded operator acceptance can establish a prospective inherited scope reference without changing historical assurance truth.

Accepted-requirements/ADC owners resolve exact revision, purposes, **effective limiting/prohibitive criteria**, explicitly authorized real protection reductions and relevant competent exceptions. AEV qualifies material-change mapping and protection-preserving equivalence, without treating every removed line as immutable policy. An apparent conflict is NONCONFORMING only where the restriction's effective applicability is qualified after competent exceptions or supersession capable of affecting it. If a potentially competent exception is inaccessible, the dependent conflict/positive remains NOT_ESTABLISHED; a qualified non-waivable breach remains NONCONFORMING regardless of irrelevant exception uncertainty. A change within an execution grant is still subject to scope qualification.

A protected mechanical path can resolve a bounded, corroborated-inert edit without another assessment agent when its comparison, source bytes, baselines and rules cannot be shaped by the implementing lineage. An authorized implementing-lineage self-check remains attributable evidence, not an independently authoritative scope verdict. When material mapping needs judgment instead of a qualified protected mechanical result, the determining assessor must be eligible and outside the implementing root-grant lineage. The existing ADC/AEV independence floor applies without relabeling self-checks as independent verification.

### 4.2 Outcomes are not synthetic workflow states

| Scope determination | Semantics | Consumer implication |
|---|---|---|
| **CONFORMING** | Qualified cumulative package change and relevant inherited scope/pedigree or direct assessment, eligible assessor, applicable purpose and effective limiting constraints, comparable relevant authority/exception closure and exact evidence support the **declared bounded scope** | Satisfies only that G1 scope/obligation; any unassessed pre-G1 inherited material or excluded protection remains explicitly unqualified, never retroactively PASS |
| **NONCONFORMING** | Qualified evidence establishes actual conflict with a **currently effective** restriction after relevant competent exceptions/supersession, or lack of authorization with qualified applicable closure; non-waivable proven violation is independent of irrelevant unknown exception records | Withhold affected progression; preserve evidence/remediation; issue HOLD only under separate adopted rules |
| **NOT_ESTABLISHED** | Required bounded inherited scope acceptance/assurance/direct check, comparator closure, effective restriction or potentially competent exception applicability, evidence, eligibility or comparability is missing | Withhold dependent positive; explain qualified missing basis without inventing PASS or breach; unrelated independently proven adverse findings survive |

A bounded **no-material-change** result is possible relative to a protected accepted base with qualified applicable inherited assurance, directly assessed inherited content **or explicitly accepted inherited scope under its recorded limitations**. The last route can support only a *post-baseline bounded change-conformance claim*, not historical inherited G1 PASS, unexamined security compliance or a blanket whole-package clearance. A Lead-declared starting point or submitter-supplied ancestor remains NOT_ESTABLISHED. Green technical tests do not change these conditions.

### 4.3 Currentness and authoritative use

The AEV producer's **owner-authenticated, evidence-qualified** statement is bound to its exact inputs, protected source observation and applicable coverage; source change/closure epoch changes require renewal or explicit qualified applicability. The API may shorten usable currentness, not originate it. CNI checks still-applicable AEV obligation at the existing protected consequential admission; a read API can display historical or not-established with qualified disclosure, but cannot decide progression. This amendment does not mandate one global atomic snapshot across owners.

### 4.4 Runtime qualification remains separate

This is a **design allocation**, not proof of live G1 capability. G1 remains OPEN until an eligible, independently observed implementation demonstrates protected accepted-base selection **and pedigree**, cumulative byte/closure verification (including generated artifacts and repository-controlled diff-filter attacks), complete relevant governing constraints, qualified assessor eligibility, correct negative/unknown outcomes and safe CNI effect-time consumption. G2, G3 and G4 remain OPEN and independent; a G1 producer PASS does not qualify them. The D-01 read-first website may show a truthful `NOT_ESTABLISHED`/unsupported G1 view until implementation is qualified, but its entire useful read capability cannot consist only of unavailable states.

## 5. Reviewer acceptance questions

1. Can two independently built assessors agree which *source facts* must be qualified without relying on the submitter's manifest as exhaustive?
2. Can a conforming, in-grant routine edit progress without an unnecessary individual approval or universal test rerun?
3. Is an out-of-scope but technically working package refused without letting Assurance rewrite the accepted work objective?
4. Does the result bind exact observed package, **owner-derived protected base and inherited assurance pedigree**, cumulative delta, accepted revision, qualified constraint/authorization closure and comparator coverage?
5. Do missing/unknown authorization records, assessor inputs and baseline provenance stay NOT_ESTABLISHED (rather than a fabricated breach, HOLD or PASS), while established conflicting restrictions remain NONCONFORMING?
6. Can CNI consume the determination for one current consequential admission without inheriting AEV authority or bypassing G2?
7. Can an independent verifier preserve confidential drafts while reporting authorized final consequences?
8. Is parent/composed package conformance distinct from child-only success?
9. Does G1 remain open after paper adoption until a qualifying operational demonstration, including provisional-ancestor, hostile diff-driver and omitted generated-output probes?
10. Can a pre-G1 protected `main` be accepted as **bounded initial inherited scope** only by a competent operator's separately documented exact-byte decision, without historical G1 PASS or protection waiver?
11. Does deleting an effectively redundant protection with qualified equivalence differ from actual bypass or removal of an operationally protected safeguard?
12. When a potentially competent exception is inaccessible, can reviewers distinguish dependent NOT_ESTABLISHED from a separately proven non-waivable NONCONFORMING?

## 6. Adoption and dependencies

**Recommendation for review, not adoption:** This candidate should be independently challenged, then separately submitted to the operator for possible adoption as an **additive amendment to AEV v0.3.1**, preserving the ten pinned adopted normative sources unchanged. If adopted, this becomes a separate eleventh normative source until any later authorized consolidation; it is **not** a full revised AEV contract and does not silently alter original clause IDs. G1 qualification and actual implementation remain separate. The D-01 read-wire/specification effort may proceed on already-adopted semantics while it awaits this focused amendment, but it must not assert positive scope-conformance readiness until G1 truly qualifies.

**Additional operator action later (not made by adoption of this amendment):** If the first production G1 run needs to use pre-G1 accepted `main` as an inherited scope starting point, the competent operator must make an **explicit, separately pinned and dated as-built scope-baseline decision** naming the exact protected bytes, applicable scope, exclusions, adverse findings and outstanding qualifications. No supplied review asserts which current `main` bytes are eligible. Adoption of this amendment by itself does **not** accept any baseline or waive current controls.

**Pending implementation design (not required to adopt this semantic producer allocation):** exact on-wire schema, source credential mechanism, qualified comparator implementations, observation intervals, assessment runner integration, eligible assessor assignment, test fixtures/automation and deployment profile. These must satisfy the independently implementable producer obligations without inventing new rights.
