# AEW S-01 — Portable Hosting and Deployment Profile Contract

**Version:** candidate v0.2.1 · **Date:** 2026-10-17 · **Stage:** **PROPOSED NORMATIVE DEPLOYMENT/QUALIFICATION CONTRACT; NOT ADOPTED.**

**Intended scope:** Common, implementation-independent hosting **profile composition and qualification** under the already-adopted HEB/ADC/other boundary contracts; a general non-company deployment binding and an organization-specific native Rocky 8/mTLS binding. This is **not** a new universal OS requirement, a replacement for HEB, a selected release activation, a frozen public API/wire, or a claim that any profile currently conforms.

**Adopted sources (non-exhaustive):** HEB v0.3.1 (`HEB-01`, `HEB-02`, `HEB-03`, `HEB-07`–`10`); ADC v0.3.1 (`ADC-01/02`, `ADC-08`); AOI v0.2.2 (`AOI-03`–`06`); WIS/CNI/AEV; D-01 v0.3.2; K-01 v0.3.3; P-01 v0.2.1; R-01 v0.2.1 (`R01-08/09/43`); RX-01 v0.2.1. The separately operator-confirmed 2026-10-17 OpenCode/mTLS dependency is a *selected company integration constraint*, **not** a seventeenth normative source. Historical F18/F28/Q12 and the S-01 v0.1 scoping note are design evidence, not an independent amendment to adopted law.

## 0. Product outcome and qualification discipline

One AEW product must be useful both outside work and on the first workplace release target. **The same work/grant/effect, assurance, research, knowledge, resource and operator contracts apply in both settings.** Differences in OS, harness, provider, deployment controls and organizational credentials are explicit *bindings* beneath those contracts. Protected capabilities require independent evidence per effective host/profile/route; a simulation, network-compatible model call or familiar API response does not certify isolation, authority, trusted reads or billing.

Use three independent axes, not two forks of AEW:

1. **Release binding:** `GENERAL-LOCAL` (non-organization, provider/host independent) or `WORK-ROCKY8-MTLS` (first company target, including pinned OpenCode integration). These names designate proposal-level *configuration intent*, not automatic capabilities. The workplace profile **refines** the portable obligations rather than replacing them.
2. **Capability qualification:** each specific protected effect, source read, operator action, credential custody, model route, meter, or verifier path reports its own selected-profile evidence and present status. There is no deployment-wide `secure=true` shortcut.
3. **Execution lane:** functional/mock/deterministic validation; independently qualified protected agent operation; or **explicitly operator-elected external/manual work** under `HEB-02.k/l`. These lanes must remain distinguishable in CLI, API, website and evidence. Development mode is not an agent-selectable security bypass.

### Current known facts versus proposed target

- **Known adopted requirements:** HEB forbids protected mutable activation without demonstrated effective isolation and protected owner paths; agent-controlled same-UID workspace records cannot self-qualify; ADC and R-01 impose real hard-resource-control conditions; D-01 and G1–G4/W1–W5 remain unqualified.
- **Known work integration decision:** organizational upstream requires mTLS; required pinned OpenCode 2.0.18 cannot be relied on to originate upstream mTLS, so an originating mediation/gateway is a requirement for that work combination. Codex direct mTLS remains unverified. This is *not* an assertion that a gateway or credential custodian has been deployed.
- **Proposed implementation-independent split:** common hosting profile contract and two named deployment bindings; exact kernel isolation, services, certificate store, provider SDK, API fields and rollout scope require separate evidence and decisions.

## 2. Profile-selection, portability, and qualification obligations

**S01-01 — Portable product identity.** AEW SHALL retain the same adopted canonical identities, authority rules, effect intent, refusal semantics and recipient duties across general and workplace bindings. OS, harness, network and provider identifiers SHALL remain typed deployment attributes, never hidden substitutes for work/grant/operation identity. (HEB-01.c/f, WIS, ADC-02; R01-02/08.)

**S01-02 — Named effective binding.** A selected deployment manifest SHALL bind a stable profile ID/version, release context, host and security principal, harness and effective config digest, reachable effects/tool paths, provider route, credential boundary, protection evidence and applicable capability classes. Its `observed_basis.writable_reachability_digest` or equivalent SHALL identify an observed effect surface with an independently qualified completeness basis under S01-09, not only a harness-authored inventory or hash. Actual selected/observed/qualified fields SHALL be distinguishable. (HEB-01.c/f/g, HEB-03.a/o.)

**S01-03 — No broad profile inheritance.** A success on a host, model route, probe harness, account, OS, container or earlier version SHALL NOT establish protected capability on a different combination without demonstrated comparability. A workplace binding MAY add requirements but SHALL NOT relax the adopted portable security floors. (HEB-01.f/g, HEB-03.g/o, ADC-08.e.)

**S01-04 — Per-capability honest status.** A profile capability claim SHALL distinguish `QUALIFIED`, `FUNCTIONAL_ONLY`, `NOT_ESTABLISHED`, `UNSUPPORTED`, `UNAVAILABLE`, `STALE` and `REFUSED` *semantically* (illustrative names, not frozen wire). A supported API shape or working mock SHALL NOT be exposed as protected positive admission; limitations and the independent evidence basis SHALL be visible to authorized recipients. `FUNCTIONAL_ONLY` is a description of compatibility or local function, **not** permission to dispatch a chargeable AEW-controlled effect contrary to currently applicable grants, operator resource policy or disclosure conditions; S01-14 and S01-24 apply independently. (HEB-01.e/g, ADC-08.b/e/j, R01-43, AOI-03.)

**S01-05 — General local is a real use target.** `GENERAL-LOCAL` SHALL offer a workable path to project orientation, deterministic simulation, provider/harness integration, CLI/API/website fixture tests, and source- and entitlement-safe reads without organizational mTLS dependencies. Where the host passes independent protected conformance it MAY run the qualified protected subset; where it fails it SHALL not claim protected work and SHALL preserve useful explicitly operator-elected external/manual contributions under HEB-02.k/l without agent-selected automatic fallback. (HEB-02.h/i/k/l, HEB-04, AOI-03.)

**S01-06 — Work binding is a refinement.** `WORK-ROCKY8-MTLS` SHALL explicitly bind the native Rocky 8 host configuration, approved work harnesses, organizational mTLS API, source/credential host boundaries and selected work release functions. The pinned OpenCode/org API combination SHALL have an originating mTLS mediation path; inability to connect is a **failed required harness integration**, not a reason silently to drop OpenCode or pretend OpenCode directly supports upstream mTLS. Other harness paths may be separately qualified but do not discharge this requirement. (HEB-01.c/f, HEB-03.e/k, operator mTLS constraint.)

**S01-07 — Capability matrix is not a grant.** Release manifests, status projections, host inventory, and vendor success claims SHALL NOT mint worker grants, permit execution, clear holds, accept source evidence or change operator authority. Actual consequential effects still require current ADC/HEB admission and applicable WIS/CNI/AEV/R-01 decisions. (HEB-01.d/e, ADC-01/02/08, CNI-03.g.)

## 3. Effective enforcement and credential trust

**S01-08 — Protected path must be independent.** Each protected writer, request binder, result/checker, operator origin or credential custodian needed by a qualified claim SHALL be outside the relevant model-controlled lineage's write, substitution, bypass and runtime-interference reach, *including effective runtimes, libraries, env/config loading, process/IPC and final delivered result*. Same-UID agent-writable files, Git hashes or tool naming alone SHALL NOT provide this qualification. (HEB-01.a/h/i, HEB-03.e/i/l/m/p/q, P01-37.)

**S01-09 — Complete effect path inventory.** Qualification SHALL test all accessible native harness, shell, tool-server/MCP, plugin, subprocess, filesystem, Git, IPC, peer-process, network and model-SDK routes at actual effective agent identity, including indirect and alternate invocation. The **inventory and its completeness boundary** SHALL be independently observed or qualified by a competent host/effect observer outside the measured lineage's ability to write, omit, substitute or interfere with the observation and final result; a digest or route list supplied only by the measured lineage SHALL NOT establish completeness, including when each listed path passes its own test. The `observed_basis.writable_reachability_digest` under S01-02 SHALL bind that independent observation and exact effective surface. Missing independent coverage, an omitted reachable route or untested bypass means affected protected claims are `NOT_ESTABLISHED`; changing the effect surface invalidates affected qualification before reuse. Host/OS mechanisms are selectable, not assumed from this text. (HEB-03.a–q, ADC-08.j.)

**S01-10 — Independent request binding.** Protected effect admission SHALL use owner-qualified current work/revision, actor, grant/generation, exact operation, arguments, destination and corresponding effect intent; attacker-supplied headers, API keys, local filenames or model metadata may transport data but SHALL NOT on their own establish authority. Revoked or stale actor/operation input fails before the effect. (HEB-01.d/e, HEB-07/08, ADC-02/08.)

**S01-11 — Work credentials protected.** Work upstream mTLS key/certificate, gateway ingress credentials, protected policy and any meter settlement authorization SHALL be inaccessible to agent-controlled Lead/worker processes and their reachable helpers. Selected ingress/endpoints SHALL authenticate actual authorized callers, scope recipients and destinations, rotate/revoke credentials, and refuse direct, leaked-key or alternate route bypass. An on-guest gateway under the same accessible UID is not automatically a trusted custodian. A work-selected same-UID gateway whose running credential can be reached by an agent SHALL remain **transport-only, with credential-custody/non-bypass claims NOT_ESTABLISHED**; encrypted storage and an interactive startup unlock can reduce accidental at-rest exposure but do not protect an active credential from that agent. The qualification requirements in this clause are not waived by that deployment choice. (HEB-01.a/h, HEB-03.e/j/k, R01-08, IF-12 operator constraint.)

**S01-12 — Connectivity and metering separate.** Model transport SHALL have distinct qualified outcomes for protocol/streaming compatibility, upstream mTLS peer/certificate success, credential protection, trusted request identity, non-bypass, and independently observed usage/settlement. Passing the first two SHALL NOT imply a trusted R-01 meter or an AEW effect grant. (HEB-03.c/e/k/n, R01-08/09/43.)

**S01-13 — Different meter adapters, same accounting.** `GENERAL-LOCAL` direct-provider or mock and `WORK-ROCKY8-MTLS` gateway/provider paths SHALL preserve the same R-01 original-intent/parent-scope/unknown-cost semantics. A direct provider MAY qualify an independent meter **only if all chargeable routes for that admitted class are non-bypassably covered** and its access, billing, protected operation attribution and settlement provenance meet R-01; functional direct access, provider SDK self-report or a second unmetered route SHALL NOT qualify the meter or reduce encumbrance. Missing meter must not disable honest cooperative accounting or source-only development. (R01-05/08/09/31/43, ADC-08.f.)

**S01-14 — Protected resource class conservatism.** No work or general local resource class SHALL show `RESERVED`, remaining hard-cap headroom, enforced concurrency or guaranteed budget unless its admission writer, scope aggregation, actual effect gate, worst-case bound and independent meter/settlement are qualified for that class. Work gateway availability by itself changes none of those predicates. **Real AEW-controlled paid inference, including testing or functional-only invocations, SHALL be admitted under the actual current operator-selected policy for its original operation, resource class and relevant parent limits.** An applicable mandatory hard cap without a competently enforceable admission/worst-case bound and effect gate SHALL refuse/hold the affected paid dispatch; cooperative telemetry or a `FUNCTIONAL_ONLY` status is not a cap waiver. An expressly operator-authorized cooperative/non-hard class MAY operate only if all otherwise applicable ADC/HEB, provider, disclosure and resource conditions for that exact class are satisfied, with truthful unqualified meter/accounting disclosure; this exception cannot be self-selected by a worker, harness or profile label. **An exception SHALL be grounded in an explicit operator-issued policy decision, external to the measured agent lineage, identifying the effective accountable scope, class, allowed provider/account and recipient, bounds, applicable period/expiry, and known loss of enforcement; a mutable runtime setting is only a projection, not a new approval.** Where that decision or its applicable comparison cannot be established, no edited local flag may authorize a cooperative class; an honestly disclosed operator-elected cooperative workflow is not a protected hard-cap claim, and divergence is an attributable configuration defect. Mock/offline no-charge tests and genuinely operator-elected HEB-02.k/l external/manual activity remain different lanes, not AEW-paid-effect exceptions. (R01-07/08/09/39/43, ADC-08.f/i/j.)

**S01-15 — Trustworthy operator origin separate.** Operator-only command effect authority SHALL require independently qualified exact human-origin display/input and request binding; a login, local UID, website button, request token or gateway identity alone cannot discharge G3. Where unqualified, protected operator decisions stay held, while independently safe read-only/functional paths can continue. A mutable deployment descriptor may **display** an attributed G3 capability report, but never itself establish operator-origin qualification or authorize the corresponding command; the competent protected issuer, recipient and current operation binding must be checked independently. (HEB-01.b, AOI-03.e, ADC-01/08.)

**S01-16 — Safe outage, revoke and handoff.** Missing model/gateway, issuer, host attestor, meter or reader SHALL not create alternate effect paths, fresh grants, free budget, negative exposure or live status from historical data. Hold affected protected effects, reconcile original operations and held results across drain/detach/reattach, preserve qualification of genuinely independent unaffected capabilities. (HEB-01.e, HEB-07/08, R01-08/31/43, CNI-03/05.)

**S01-17 — Source and disclosure independence.** Current qualified source/status, G1 material package, W4 protected read, G4 outage reader, assurance, map and Knowledge claims SHALL be grounded in their competent owner/integrity qualification, source basis and exact recipient entitlements. A service mounted on the work VM, a valid D-01 response or a functioning personal mock cannot independently certify these claims. Model request context is a **disclosure to the exact provider/account/recipient route**, not a neutral local read: competent source/work-policy owners SHALL determine entitlement to disclose each governed source or tool-derived content under the effective work/general release context, regardless of who assembled the prompt or selected the environment label. This requirement covers request bodies, prompt fragments, tool outputs, streamed material, retries, diagnostics and logs; an unqualified route or unknown recipient entitlement withholds the affected disclosure without treating the gateway as the source-policy authority. Positive enforcement depends on proved read and egress mediation under HEB; do not imply semantic DLP on an unrestricted host. (HEB-01.a/e, HEB-10, D-01, AEV, K-01, P-01, AOI.)

**S01-18 — Test results must survive the attacker.** A conformance checker and the proof presented to the operator/reviewer SHALL be protected from the lineage whose effects it measures; a result saved in the tested agent's writable space cannot by itself authorize a positive qualification. Tests SHALL include runtime manipulation, result substitution, untrusted config and alternate endpoint variants. (HEB-01.h, HEB-03.g/i/o, P01-37.)

## 4. Portable consumer contract, lifecycle and release control

**S01-19 — Typed profile declaration.** The selected profile contract SHALL expose versioned machine-readable *declared*, *observed* and *qualified* facts by capability and effective binding, including issuer, currentness/epoch, source evidence, test scope, decision owner, negatives and unsupported/degraded behavior. An unselected example JSON/schema SHALL NOT be misrepresented as a frozen runtime API. (HEB-01.f/g, HEB-09/10, AOI-03/04.)

**S01-20 — Comparable positive and negative fixtures.** Before protected activation, a selected profile SHALL have reproducible benign positive and attacker-origin negative tests for each enabled class, exercised under the actual effective agent identity and reachable routes. Tested constraints SHALL include same-UID/peer process, credential exposure, tool/harness hot changes, lost responses, revoked grant, source freshness and result-path tampering as applicable. A mock passes functional semantics, not host protections. (HEB-02.i, HEB-03.g/o, HEB-10, ADC-08.j.)

**S01-21 — Operator and website are equal consumers.** CLI, backend, website and harness agents SHALL consume one shared capability/qualification source contract, with recipient-qualified projection and uncertainty. A UI's “ready” status is not an owner decision; neither backend nor website may invent default security support or silently reinterpret profile statuses. A website can be developed and tested with shared fixtures independently of the work gateway. (AOI-03–06, D-01, HEB-09/10.)

**S01-22 — Profile transition is an actual transition.** Switching work/general context, harness **or plugin/version**, adapter, model account, toolchain, process principal, protected writer or endpoint SHALL create an attributable new effective profile/basis and recheck applicable authority and qualifications. An operator's requested selection SHALL remain distinguishable from an AEW-confirmed effective configuration; a website save or pending operation cannot report activation before the competent protected transition/qualification succeeds, and no current GET-only D-01 route implies protected writes. It SHALL not carry stale credential access, protected lease, release grant or read/currentness witness across a noncomparable transition. Unaffected canonical work and externally admissible artifacts may be reused with correct identity and reconciliation. (HEB-01.c/f, HEB-02.e, HEB-03.o, HEB-07/08.)

**S01-23 — No implicit policy promotion.** A deployment profile SHALL NOT choose for the operator which proposed features are due, grant a risk-class downgrade, supersede a historical operative safety control, or widen trusted operator access. Each such change requires the applicable competent operator/adopted policy decision and separate evidence. (ADC-01/05/08, HEB-10, architecture governance.)

**S01-24 — Profile composition requires complete gates.** When an operation composes several profiles (e.g., worker isolation + model route + meter + shared fixture), positive consequential admission SHALL require qualified comparable evidence for **all** required gates at the same original operation/effect boundary; AEW-controlled chargeable inference SHALL separately satisfy the **actually applicable resource policy** even when host code-write protection is unavailable and model transport is functional, and external model payload delivery SHALL satisfy current owner-qualified recipient/disclosure policy, including the actual destination and model account; partial gateway or partial resource reservations cannot become dispatch. Unknown or contradictory component facts hold the affected effect without gratuitously stopping proven-independent safe work. (HEB-01.d/e, CNI-03.g, R01-07/39, ADC-08.i.)

**S01-25 — Capabilities are not universal booleans.** Profiles SHALL represent selected scopes for individual effects, reads, issuers and recipients; supporting source-only inspection, scoped result retention or a model call does not imply safe editing, trusted reviewer execution, protected operator origin or comprehensive model-cost enforcement. Capabilities and proof must remain independently requalifiable. (HEB-01.g, HEB-02.h/i, AOI-04, R01-43.)

**S01-26 — No work-only secrets in general artifacts.** Work-only private endpoints, credentials, certificates, restricted provider data or protected operator/work artifacts SHALL NOT be transported into general local profiles via packaged manifests, fixtures, errors, logs or copied configuration. Cross-environment migration **and live model payload egress** require competent source/work classification and recipient entitlement, exact model/provider/account destination qualification, and explicitly approved sanitization or isolation where applicable; identifiers may be transformed only with provenance-preserving mapping. Profile labels, `environment_kind`, client metadata, saved website selection, and success on a transport-only gateway SHALL NOT downgrade work-source restrictions or authorize disclosure to a personal provider. Egress, prompt assembly, retries, streaming, tool-context transfer, logs and provider diagnostics need recipient-safe handling at their actual delivery boundary. If effective recipient or non-bypass coverage cannot be qualified, refuse/hold that disclosure; source-only and independently permitted public-data routes remain usable. (HEB-01.a, HEB-03.j/k, AOI-04, WIS/CNI.)

**S01-27 — Qualified developer/production parity is behavioral, not environmental.** Common schema and semantic fixtures SHALL run independent provider and consumer implementations under both bindings with the same allowed/denied *contract outcomes* given equivalent facts; differences in real protection evidence SHALL remain explicit rather than normalized away. Successful functional or simulated parity does not transfer G1–G4 or D-01 W1–W5 qualification. (HEB-01.f/g, HEB-10, D-01, AOI.)

**S01-28 — No gateway-only critical dependencies.** Core work identity, accepted-scope/progression rules, evidence and resource accounting SHALL not depend on a workplace gateway being reachable or existing in `GENERAL-LOCAL`. Different transport and meter adapters SHALL preserve canonical semantics, with an honest `NOT_ESTABLISHED` class wherever direct-path hard limits lack qualification. (WIS/CNI/AEV, R01-08/43, HEB-01.e.)

**S01-29 — No automatic insecure fallback.** When the work gateway or protected host path fails, AEW SHALL not silently switch to agent-readable upstream keys, another model identity, a personal subscription, unconstrained shell, locally issued grants, or operator-impersonating UI. Any explicitly operator-elected external/manual task stays outside AEW-protected execution and is admitted later as untrusted contribution. (HEB-01.e, HEB-02.k/l, HEB-03.e/k, ADC-08.j.)

**S01-30 — Exact release gate recording.** Any qualified profile release SHALL record exact subject/profile/host/harness/provider version, permitted operations, operator-selected applicability, genuine evidence issuer, test time/currentness and invalidation triggers; unqualified gate rows SHALL remain open without negative claims that unrelated functions fail. Separate host G1–G4, D-01 W1–W5, R-01 and P-01/RX-01 claims stay distinct. (HEB-01.f/g, HEB-10, AOI, architecture register.)

**S01-31 — Unified operator startup unlock.** A selected interactive deployment SHALL support **one operator-facing startup unlock/session preparation** for normal AEW use, orchestrating access to the locally configured AEW services, model adapter/gateway and eligible nonprotected workflows without separate routine component passphrase prompts. Its input, credential activation, scope, expiry/lock/restart behavior and failures SHALL be operator-visible and profile-bound; secrets SHALL not be copied into agent-authored configuration, logs or prompts merely to avoid repeated entry. A short PIN without independently qualified rate limitation or hardware-backed key protection SHALL NOT be claimed sufficient to resist offline guessing of encrypted credentials; a stronger passphrase or other qualified authenticator may be required for that property. On a shared-UID host an unlocked local secret remains **agent-reachable**, so one unlock does **not** certify agent-resistant custody, operator-origin G3, protected G2 execution, model admission, spend authorization or ongoing grant. Independently required human-only decisions retain their own protected authorization channel even after routine startup unlock. Exact startup secrets and UI mechanisms are selected-profile details. (HEB-01.a/b, HEB-03.e/j/m, ADC-08.j, AOI-03/06, S01-15/22.)

## 5. Deliberate non-connections and legitimate operations

- Do **not** require workplace certificates, Rocky 8, the company CA, or a universal proxy in `GENERAL-LOCAL`.
- Do **not** create a universal model-usage truth service merely to make gateway and direct accounts look identical.
- Do **not** treat an approved model inference for a test as an independent grant to create another writable agent.
- Do **not** treat a functional local or mocked AEW run as HEB-protected code-edit conformance; preserve legitimate operator-directed manual engineering and later normal admission.
- Do **not** force an LLM to remain awake to monitor conformance; independent host/source probes can be deterministic.
- Do **not** equate mTLS client authentication, operator-origin authentication and per-operation authorization.

## 6. Selected-profile and implementation decisions held open

`S-DEC-01` release functions/due gates; `S-DEC-02` actual protected work writer/executor under shared-login Rocky 8; `S-DEC-03` trusted operator-origin and safe independent reader; `S-DEC-04` IF-12 workplace gateway ingress/upstream mTLS/placement/rotation; `S-DEC-05` qualified R-01 resource and meter classes per environment; `S-DEC-06` developer/general-local execution host coverage and supported qualification. No self-contained selected-profile schema above supersedes the adopted D-01 or constitutes a protected O-01 command wire. A separate release applicability record and actual host/gateway/security evidence are required for first deployment.

## 7. Adoption and conformance boundary

Adopting S-01 in the future would adopt *profile composition and qualification semantics only*. It would **not** activate OpenCode, a protected gateway, resources, trusted reads, website commands, effectful research, secure local development or a new first-release workload; nor make a system with unprotected same-UID writers safe. All **31** `S01-01`–`S01-31` candidate obligations are proposed, with scenario expectations unexecuted. **G1–G4 and D-01 W1–W5 remain OPEN.**
