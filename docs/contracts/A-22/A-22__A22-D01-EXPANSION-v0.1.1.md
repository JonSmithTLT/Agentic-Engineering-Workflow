## 1. Derivation: outcomes first, before URLs

**J-CAP:** The operator, agents and independent website can determine what the selected AEW installation actually supports, what is only observed functioning, what is independently qualified, and why a dependent control cannot be used. The same record must show requested, observed and effective profile conditions without permitting the site to award G2/G3. Adopted S01-04/07/19/21, IF13-04/06/09/10/12/15/16.

**J-RUN:** An entitled operator can find which invocations are actually active, suspected stalled, wake overdue, uncertain after external work, or held in HEB custody; inspect bounded elapsed/progress and attributable cooperative/qualified usage without conflating phase, authority, control or billing. An implementing worker cannot infer the existence, timing, consumption, count or held status of independent verifier work. Adopted R01-13–15/34/36/43, HEB-06–08, AOI/D01-WR-02–18, IF10-14 and IF12-12.

**J-HIS:** The operator can see an attributable, bounded history-check observation; “no findings” applies only to the **actually inspected population and period**, never automatically to all project history. The interface distinguishes subset detection, uninspected/unknown coverage, backlog, over-policy and absent evidence from *protected integrity*. The current shared-UID scan is detection only; observed status is not cryptographic or agent-resistant audit. This is included as a subordinate installation-capability observation pending exact competent historical-audit producer/issuer selection, not a newly minted authority or a general raw history endpoint. AEV/HEB/K01 retain distinct canonical facts.

**J-MAP:** Maps/structural input-set/diff are a P01-33 selected consumer profile, not presumed D-01 baseline. Profile candidate is separately included and **not activated**.

## 2. Proposed additive guarantees (D01-EXT-01–12)

**D01-EXT-01 — Additive shape, applicability and regression law.** Subject to an explicit operator decision selecting this shared-read target (distinct from deployment), a reviewed D-01 successor MAY add the typed GET `/v1/read/capabilities`, `/v1/read/runs`, and `/v1/read/runs/{execution_id}` with list/list/detail envelope semantics, increasing the proposed operation count 14→17. These are new shared-product reads, not old API aliases. All old 14 operations, D01-WR-01–30 protections, and competent producer authority remain unchanged; there is no universal `control_revision` or new write endpoint. The operator decision SHALL distinguish adoption of the 3-route logical extension from separately selected exact executable OpenAPI wire/profile and actual deployment; the provider and website cannot independently decide that a route is optional. A successor version/consumer negotiation is required before deployment; 0.3.2 is still the adopted implementation target.

**D01-EXT-02 — Capability owner decomposition.** S01/IF13 provide declared profile identity, actual observed binding, transition and effective state; the competent outside-lineage assessor/host/control issuer provides the qualification of each exact capability/scope/effect route. R01/HEB/ADC/recipient owners supply their own independent constraints. `capability` is a read projection keyed by a typed profile-capability reference, not a grant, policy, protected-controller or global installation certificate. Qualified statuses must resolve to current qualified source, scope, coverage, issuer and independent evidence. Unqualified source shape or agent-minted issuer string does not count. The capability list SHALL not flatten requested/observed/qualified/effective into one `available` boolean.

**D01-EXT-03 — Capability negative and absence.** `FUNCTIONAL_ONLY`, `NOT_ESTABLISHED`, `STALE`, `UNSUPPORTED`, `UNAVAILABLE`, `REFUSED`, `HELD`/`UNKNOWN_EFFECT` affect only relevant capability/route. Operator-visible limitation classes may be typed, but missing protected status or provider absence never supplies either qualified or no-conflict evidence. Hidden optional host paths, sources, private scopes and principals do not surface through roster entries, count, order, reason or timing classes. A positive complete visible capability set requires a current recipient-qualified collection membership proof; otherwise return partial/unknown, not qualified empty.

**D01-EXT-04 — Run producer separation.** R01 is competent for supported run observation, stall suspicion, wake status and resource progress; HEB supplies attachment/custody/close/drain states; IF10/R01 supply monetary/cooperative/provisional/unknown charge facts; WIS and ADC supply original accepted work/grant lineage when disclosure permits. The backend correlates by exact invocation/operation/profile generation; it cannot rewrite a worker `active` report as qualified active, infer an expired grant from process liveness or turn custody `HELD` into published result. An execution phase SHALL carry a typed `phase_observation_class` (`HEB_OBSERVED`, `AGENT_REPORTED`, `MODEL_INFERRED`, `UNKNOWN`, `WITHHELD`) and the exact competent observation basis/epoch. `OBSERVED_*` phases require an attributable HEB-origin process observation; a heartbeat or run-directory report from an agent is `REPORTED_*`, and model inference is not observed liveness. Phase, stall/wake suspicion, possible remote effect, custody and resource exposure SHALL be separately representable and simultaneously true, each with its relevant owner, source epoch, and bounded unknown/withheld semantics. `HEB_OBSERVED` is an attribution class, not a declaration of G2 host protection. Duration is bounded observed elapsed information, not a global wall clock proof.

**D01-EXT-05 — Run collection and detail.** The list and detail refer to canonical `execution_activity` IDs, with the exact D01-WR-06 canonical base64url path representation and all disambiguating known source dimensions retained in the record. `GET /runs` includes only recipient-eligible scoped invocations. An authenticated exact detail for an absent or undisclosable invocation is indistinguishable 404; an unqualified source fact for a known permitted invocation is a limited 200 when safe, otherwise 503. Pagination retains D01-WR-17–18 identity/ordering and qualified membership rules. A detail link is serialized only when that exact full target is currently navigable.

**D01-EXT-06 — Privacy, private review and custody.** Private reviewer run presence, elapsed/progress, cooperative token usage, budget, activity timing, held result and parent-pool cardinality are confidential even as aggregates and cursor invalidations. Recipient-safe visible projections and page membership are computed *after* disclosure scope. An operator with separately qualified read entitlement may see the owner-qualified custodian state needed for a response, without having publication or G3 rights. A shared-UID replayable browser token is limited to the intersection of plausible holder privileges under D01-WR-02–04; never “operator” merely because the request bears that token.

**D01-EXT-07 — Recipient-visible version continuity.** No response field, pagination version, cursor expiry, ETag, error distinction, `valid_until`, link presence or result cardinality may depend on changes invisible to the effective recipient. A cursor binds recipient + assignment/lineage + filters + disclosed membership/order/source epoch and must be tamper-evident or qualified opaque server-held, not raw unsigned base64url. A historical pinned sequence does not bypass entitlement revocation. The old global `control_revision` hot-cursor policy is incompatible and MUST NOT carry into this successor.

**D01-EXT-08 — No conditional-read adoption by accident.** The candidate does **not** introduce HTTP 304, HEAD, conditional authorization, an offline protected response cache, or altered D01-WR-01 `private, no-store`. An optional future ETag/304 profile requires a separate reviewed response/status/cache-currentness and recipient-matched noninterference contract, including no requalification of stale sources from a 304. This is independent of adding three reads.

**D01-EXT-09 — Bounded historical detection versus protected integrity.** History audit result `OBSERVED_NO_FINDINGS`, `BACKLOG`, `OVER_POLICY`, `UNKNOWN`, `UNAVAILABLE` MAY be a subordinate `history_audit` observation, **not** a new history or certification authority. Any non-UNKNOWN/UNAVAILABLE observation SHALL be traceable to an attributable actual checker/producer and evidence/run identity, exact **inspected** history population or immutable inspected-set reference, period/epoch, inspection bounds, scope coverage, and known exclusions/omissions. The governing original source owner, not the website, establishes source-set membership; a checker cannot claim completeness merely from what it happened to read. `OBSERVED_NO_FINDINGS` SHALL mean only **no finding detected within that identified inspected set over that recorded interval**. An unknown, missing or unbounded inspected set/provenance prohibits positive no-findings even at detection-only grade. Where the requested whole-project history is larger, unexamined, or of unknown completeness, that requested-scope result is `UNKNOWN`/partial; it may coexist with a separately and clearly delimited subset-specific detection observation, but never a project-wide all-clear. Backlog/over-policy detection is likewise confined to its attributable inspection scope. Counters are recipient-safe, nullable fields; null is unknown/withheld, never zero, and neither withheld counts nor excluded private history may leak through aggregate, status, cursor, or scope labels. On the current shared-UID baseline `TAMPER_DETECTION_ONLY` or `NOT_ESTABLISHED` remains mandatory: an agent-reachable report or hash is not protected audit. Any `QUALIFIED_PROTECTED_SCOPE` claim additionally requires independently qualified producer, source completeness and custody for that **same scope and period**; the site, `reasons.py`, and IF-13 capability presentation cannot issue it. In the absence of even attributable bounded detection, `history_audit=null` or `UNKNOWN` is valid and other reads continue. Audit observations never issue G1/G2/G4 or Knowledge admission.

**D01-EXT-10 — Read envelope and error inheritance.** New operations retain the adopted 200 `ReadResult` and 400/401/404/409/503 Problem states; same controlled headers, source stamps, renewal, `field_sources`, receiver, strict schema discriminants, unknown/partial meanings and 404 nondisclosure. Neither `AVAILABLE` nor a typed reason from the prior dashboard independently establishes actual configuration, entitlement or qualified historical integrity. Canonical source semantics, not a Python registry, govern any reason mapping. No new global policy or issue service.

**D01-EXT-11 — Independent backend and website substitution.** Backend W1 and website W2 implement the *same* contract/fixtures without inferring authority from UI text, legacy JSON, demo data or `may_dispatch` booleans. W3 exercises joins from capability→run→held status and source change→read invalidation; W4 performs matched-world private-review, cursor/ETag/status/timing and bearer-replay checks; W5 demonstrates three positive operator journeys under a genuinely eligible source. A schema-valid sample is not proof of real producer qualifications or a release.

**D01-EXT-12 — Controlled profile selection and older code.** The minimum productive first-release selection, exact host/credential and policy/audit source currentness, version negotiation, error transport, optional conditional GET and P-01 map profile remain independently reviewable decisions. Compatible historical implementations may be reused after conformance checks; incompatible features (global revisions, unsigned cursor, unqualified 304) require correction rather than preservation for nostalgia. No backward-compatibility promise for legacy `/api/v1`.

## 3. Proposed wire identity and representation

Three new routes and resource families: `capability` (`SubjectRef.kind=profile_capability`), `run` (`kind=execution_activity`), with `ReadCapabilities`, `ReadRuns` and `ReadRunDetail`. Existing resource kinds and routes are preserved. The full merged `openapi-read-v0.3.3-PROPOSED.yaml` demonstrates the type-extension fit, but it is **not yet a frozen production schema**: the adopted D-01 `ReadResult` convention, new R01/IF13 source stamps, owner-versus-projection issuer protocol, relationship/field provenance and exact cross-language canonical identity all still need the selected wire's Layer B and independent qualification.

The v0.1.1 candidate also repairs the illustrative draft wire’s flattened run phase: distinct phase provenance, stall, wake and possible remote effects are represented independently, with source-issued basis still to be selected. A *structural* parser admitting a self-asserted status is a known insufficient security test. Companion examples and a bounded checker provide documentary validation only. Before adoption of a successor production wire, close the missing exact producer/issuer bindings, standalone mirrors/old corpus parity, recipient matched-world suite and selected response compatibility semantics. See `02-INTERFACES/EXTENSION-TRUST-AND-WIRE-DELTA.md`.

## 4. Reasons not to add more operations now

- `history/integrity`: subordinate observed capability for the present operator journey; separate detail only if a source-qualified positive workflow proves the card insufficient. **Canonical audit issuer/source boundary is not yet selected.**
- `overview`, `project`, `activity`: compose available reads, no competing source of truth. Event subscriptions aren't the same as GET and are not invented.
- old `/evidence`, `/history`: D-01 bounded assurance resolver and finalized Journal are present; unrestricted raw archive awaits a distinct K01/AOI qualified source/disclosure profile.
- P-01 maps: a separately selected website read profile (P01-33/37), without freezing old map URL layout, T5 implementation or promoting derived map truth into WIS/CNI/AEV authority.
