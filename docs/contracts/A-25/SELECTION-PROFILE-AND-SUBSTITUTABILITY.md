# Integrated first-release A+B extension — machine selection profile

**Status:** PROPOSED, exact-byte operator selection pending. Synthetic W0 conformance is **not** deployment approval. A-23 (17 reads) and A-24 (7 commands) remain independently adopted, byte-immutable baselines.

## Product boundaries and coverage

Scope: three additional D-01 GET operations (continuation vector, owner-operation discovery, AEV hold recovery); three additional O-01 actions (attach, reattach, reaffirm one child). No global continuation authority, no automatic grant resurrection, no O-01 operation ownership, no new functional delegation. The G3-unqualified first preview uses existing functional CLI for execution/cancel and read-only website controls. P-01 full interactive maps remain an explicit other-profile obligation; existing `aew map show` can serve functional use, not W5 website acceptance.

## Normative profile decision: exact cutover, not implicit coexistence

1. D-01 `0.3.4` is an **exact-match successor** at unchanged `/v1/read/` paths. Provider binds a route-group deployment to **one** D-01 version; clients cannot infer 0.3.3 from an unchanged URL. Every success and failure on the successor carries `X-AEW-Wire-Version: 0.3.4`, `Cache-Control: private, no-store`; wrong/absent required version selection must fail before a new payload is provided, following the documented invalid-request refusal. A separate v0.3.3 deployment, if still offered, retains the adopted A-23 contract unchanged. Discovery/rollout is operator/provider deployment configuration, not a new authority service. A caller without reliable selection must withhold, not silently parse.
2. O-01 `o01-command-0.2-review-candidate` is the **one exact successor marker** for command-set header and body, receipts and owner-operation observations. A-24 0.1 clients only send original seven actions to a v0.1 deployment; a v0.2 endpoint refuses a mismatched header/body and must not transform or dispatch it. A provider may separately host a compatible v0.1 endpoint, but cannot promise transparent negotiation on the same bare URL. No protected action is activated by version support alone.
3. O-01 remains a carrier: a 202/received/held receipt is not a HEB/ADC effect. Only an owner-issued current observation establishes admission/effect. Unknown effect must be reconciled by original `(owner, operation_ref)` without replay under another request key.

## Transport / ordering / privacy rules

- Canonical D-01 `{work_id}` and `{hold_id}` path segments are **unpadded base64url of UTF-8 exact identifier**, decoded once and round-trip re-encoded; invalid base64, padding, Unicode noncanonical encodings and double encoding are HTTP 400. Hidden and nonexistent IDs are both 404 with identical public Problem fields and timing class. Authentication failure 401, revoked/stale or unauthorized cursors 409, unavailable owner 503 where no honest limited response exists. 200 can represent truthful partial/unknown data; it cannot claim green source continuity without qualified owner evidence.
- Every D-01 resource is inside inherited `ReadResult`. `effective_recipient_ref` and each Resource.disclosure.effective_recipient_ref match authenticated receiver; all consequential `data.*` fields require owner-qualified `FieldSource` stamps. Positive `present_current` facts need external owner evidence, independent expiry and comparable scope/revision/generation; merely schema-valid issuer strings are insufficient.
- Operation list resource `data` is exactly one `OperationIndexEntry` with owner+action registry parity, A-24-compatible ID/path and source stamp from `entry.owner`. No entry owns `membership` or cursor. Outer `PageInfo` controls the recipient view and `ReadResult.collection_basis` controls qualification. Qualified empty demands owner-set closure for the disclosed scope, current issuer roster, checked digest and every covered owner's membership evidence; partial may show visible subset without a claim of global absence.
- Collection ordering is lexicographic `(owner, operation_ref)` in the recipient-visible, fixed-snapshot set, with uniqueness. Cursor identity binds recipient, filters, binding, issuer snapshot digest, owner-set version and last visible key; cursor comparison after changed snapshot fails with nondisclosing 409. Hidden-world additions must not change visible count, cursor, scope, freshness class, error, or observable timing class.
- Attach/reattach transitions are compare-and-fence atomic in the competent HEB owner's linearizable state. Successful reattach atomically fences predecessor and establishes exactly one current successor; child grants remain inactive. A stale competing attempt does not create another successor. Retry, conflict and reconciliation follow the command-set admission rules below (CS-03, CS-04, CS-08), which restate adopted A-24 SW-07; new key after unknown receipt cannot be used to double-create an effect.
- A04 is a separate ADC-owner child operation with its own operation identity and evidence. Each current successor+child+prior-grant-version may have at most one effective reaffirmation under a qualified classification; a repeat is refused `PRECONDITION_STALE` (owner reason `ALREADY_REAFFIRMED`), never `UNRESOLVED_NO_REDISPATCH`. Revoked child cannot be restored. Functional CLI delegation cannot be promoted to protected grant authority.

## Canonical qualified visible-set digest (W0 fixture profile)

For the bounded owner-index source-world snapshot, `visible_set_digest` is lowercase `sha256:` + SHA-256 over canonical UTF-8 JSON using lexical keys, compact separators, no ASCII escape conversion, of `{binding,recipient,owner_set_version,scope,owners,visible}`. `owners` is a sorted array of the scoped owner set. `visible` is an array of `{owner,operation_ref}` records sorted by `(owner,operation_ref)`. `scope` is the exact recipient-qualified query scope, not a global or hidden-owner membership assertion. It appears as `ReadResult.collection_basis.coverage_ref` and is verified against independently owner-qualified roster evidence. Hidden operations not entitled to the recipient are not included in this digest. A different scope/filter changes the digest; it must not silently reuse a previous cursor. This is a **proposed exact wire meaning**, not permission for CNI to invent absent owner attestations.

The producer-identity and expiry fields are source facts, not request strings. Fully qualified owner roster requires a closure entry for each disclosed owner, with its own competent epoch, basis and completeness; the outer `ReadResult` has the **only** collection-membership claim.


## Source, origin and refusal profile (proposed, W0; v0.5.3)

This addendum is part of the *proposed* interface selection. Where it and `OWNER-PIN-RULES.md` overlap, the owner-pin rules govern; adoption still requires an exact-byte operator decision. The D-01 0.3.4 route and O-01 0.2 command successor are not activated by these fixtures.

**Canonical owners.** Every qualified `FieldSource`, source stamp and renewal claim is a projection of the competent owner-issued record. The owner, governing owner, issuer, fact identity, epoch/version, observed time, renewal authority, renewal epoch, proof, coverage and finite expiry must match the applicable *outside-response* issuer witness. A renewal is issued by the producing owner itself (OP-04); a different owner issues its own separately stamped fact instead. A renewal epoch may differ from the source epoch only when that owner's own record lists it as comparable (OP-05). `present_current` must not be claimed if renewal has expired. A resource-level HEB source does **not** issue the owner facts in the C18 HEB/ADC/WIS/AEV/R01/IF10 axes. AEV unavailable always leaves C18 `partial/unknown`, and a reason must be an exact qualified owner reason or a bounded source-unavailable transport reason. The `informational_only` and `executable_authority` constants are non-negotiable advisory boundaries in every published schema form.

**Collection requests.** A D-01 owner-operation listing is a recipient-scoped, owner-fed projection. The qualified roster's effective query includes the explicitly normalized owner filter, attachment filter, scope filter, owner-set version, recipient, installation and cursor. A positive `qualified_scoped` claim is valid only for that exact universe with owner-by-owner closure and membership/digest/cursor evidence. A filtered HEB page cannot silently stand for the entire ADC universe. An absent/unknown owner does not prove an empty set. Any included partial closure is source-qualified even if the outer membership is `unknown` or `partial`. Navigable `(owner,operation_ref)` entries must follow A-24 O-01 identifier grammar. The index ResourceRef is a D-01 view resource identity, **not** an independent owner-operation authority ID. It is bound to the operation it names: kind `owner_operation_index`, id `ownerop:<owner>:<operation_ref>` (AB05-R05). Clients open the O-01 detail route with the explicit `(owner,operation_ref)`, and every emitted link passes O-01's own path-parameter schemas unencoded.

**Canonical command admission.** For L02/L03, a single external protected origin record must be issuer- and time-qualified and bound to the complete request, installation, recipient, consent set, client key, intent and exact target. No owner private-state comparison occurs before origin admission. HEB then checks the canonical existing attachment/predecessor state and applies one atomic compare-and-fence effect; a lost response is reconciled by reading the original operation, never by redispatching. L03 does not implicitly resume harness execution or reaffirm grants. For A04, the authenticated principal of the submitting session (CS-07) must equal the request's `actor_ref` and HEB's current successor Lead under the current successor generation, the HEB transition must agree with its predecessor fence, and ADC must separately classify each selected prior grant against scope/revision/constraints/expiry and current revocations. One child per intent yields one owner operation and one independently issued current ADC result. If crash classification is unavailable, an otherwise authorized L03 successor remains possible but **A04 holds**; a known compromise prevents reaffirmation.

**Reason and observation contract.** `new-command-refusal-reasons.json` enumerates per-command owner refusal/hold causes and maps each to an adopted A-24 reason code. The map is complete and fail-closed: every entry is produced by the admission machine, and a cause outside it is a model defect, never a default code. `new-action-refusal-observations.json` supplies full refused and HELD owner-detail specimens; origin-unqualified attempts produce no owner operation and have a nondisclosing HTTP refusal instead. A 202 carrier is receipt only, never evidence of an owner effect. Owner-operation currentness is validated against a qualified `as_of` time; expired source validity may remain historical, but cannot be displayed as current. Recipient read entitlement and the set-scoped key (CS-03, CS-04) apply to replay and reconciliation.

## Command-set admission (proposed, W0; v0.5.3, lookups revised in v0.5.4)

These rules apply to every O-01 0.2 `CommandSet`, inherited or new actions. They restate adopted A-24 SW-01, SW-02, SW-03, SW-06 and SW-07 for the 0.2 successor and add the current-successor origin; where they and A-24 differ in wording, A-24 governs. The executable reference is `03-ORACLE/command_admission.OwnerMachine.submit`, which returns either an HTTP Problem (no receipt) or one 0.2 `Receipt`.

- **CS-01 Canonical set.** One to eight intents, `intent_ref` unique and in ascending order (SW-01, SW-02). Otherwise `400 invalid_request` before any ledger, origin or owner step: no receipt, no owner operation.
- **CS-02 One origin class per set.** All members share one registry origin class: protected G3, current-successor generation, or current delegated grant. A mixed set is `400 invalid_request` (A-24 `MIXED_AUTHORITY_SET_UNSELECTED`; A-24 forbids mixing protected with non-protected members, and the successor class is a third class). A protected set carries `consent_set_ref`; any other set carries `null` (A-24 `PROTECTED_NO_CONSENT_SET`, `DELEGATED_CANNOT_MINT_CONSENT_SET`). A set mixing inherited and new protected actions is allowed; inherited members return `HELD`/`SOURCE_UNAVAILABLE` after origin in this W0 model, because their owner effects keep adopted A-24 semantics and are not modelled here.
- **CS-03 Fingerprint and key.** The set fingerprint is A-24's frozen SW-02 algorithm exactly: lowercase hex SHA-256 of the ASCII-escaped, key-sorted, compact JSON of `{request_set_ref, recipient_ref, installation_ref, intents}`. `client_request_key` is scoped to `(installation_ref, recipient_ref)` and binds the whole submitted request: the ledger stores the SHA-256 of the canonical full request. A reused key with an identical request is a lookup of the original owner operations (CS-04), with no origin re-consumption and no owner dispatch. Any difference (an intent, the member order, `consent_set_ref`, `request_set_ref`, a target) is `409 request_key_conflict` (A-24 `CONFLICT_CHANGED_SET`), never retried. `intent_ref` is not part of the key.
- **CS-04 Lookups (v0.5.4).** A lookup is any request whose key already has a ledger entry, in either mode, and every reconciliation-only request (A-24 SW-07: an identical retry is a lookup of original owner operations only). Every lookup is decided in this order: (1) the recipient's **current read entitlement** (SW-07, SW-08): if it is not entitled, or the world does not state it, the answer is the nondisclosing `404 not_found_or_not_disclosable` (A-24 `RECONCILIATION_NOT_ENTITLED_OR_NOT_ORIGINAL`), the same Problem whether the key is known, unknown, changed or expired, with no receipt, no `operation_ref` and no dispatch; (2) a missing or corrupt entry is `409 unresolved_no_redispatch`; (3) a changed request is `409 request_key_conflict` (CS-03); (4) an entry whose stored receipt is no longer valid (`source_valid_until` not after now) is `409 unresolved_no_redispatch` (SW-07: an expired ledger; expiry alone never makes a request new, so a new effect needs a new key and, for a protected action, a new consent); (5) otherwise the stored receipt (CS-08). `UNRESOLVED_NO_REDISPATCH` means only a missing, corrupt or expired entry. Read entitlement qualifies lookups only: a request under an unused key is a new submission, decided by its origin (CS-05 to CS-07) whatever the recipient's read entitlement. **Residual, by ruling (LEAD-F21):** in submit mode a recipient that is not read-entitled therefore sees a 404 for a key it used before and an admission for one it has not. The key namespace is that recipient's own, so this tells it nothing about another recipient's or an owner's private state; it is accepted rather than gating admission on read entitlement. **Narrower adopted oracle:** adopted A-24 `layer_b.py` checks read entitlement only in reconciliation mode (lines 78–80); its SW-07/SW-08 text governs here, and these rules follow the text. No adopted case has a submit-mode ledger hit with entitlement withheld (only P11 and N31 state the flag, both reconciliation-only), so `verify_adopted_replay.py` replays all 53 cases unchanged; adopted worlds that do not state the flag are replayed as entitled because the adopted oracle consults it only in reconciliation.
- **CS-05 Per-intent admission.** Members are evaluated in canonical order, each through the one admission path (origin, then owner state, then at most one owner effect), against owner state as left by earlier members. Outcomes are independent: `COMPLETE_WITH_PER_INTENT_RESULTS` is not batch success. `Receipt.results[]` has exactly one result per intent, in request order.
- **CS-06 Protected consent set.** One G3 consent record per `consent_set_ref`, issuer-qualified and time-valid, bound to the set fingerprint, recipient, installation and exact member list. Each member's `origin_proof_ref` must equal that member's proof in the record. Each member is consumed once, when its owner operation is allocated, whether the outcome is an effect or an owner refusal. Consent to one member never authorizes another.
- **CS-07 Current-successor origin.** A04's origin is the authenticated principal of the submitting session: a record issued by a trusted authenticator outside the request body, time-valid and bound to the installation. `actor_ref` is the claim being checked, never the proof. No qualified session, or a session principal different from `actor_ref`, is `ORIGIN_NOT_ESTABLISHED`, decided before any HEB or ADC state is read. The principal must then be HEB's current successor Lead (`ACTOR_NOT_CURRENT_SUCCESSOR`). The A04 schema branch requires `origin_proof_ref` and `delegated_grant_proof_ref` to be `null`: no body field carries proof.
- **CS-08 One key, one outcome.** Once a set passes CS-01 to CS-04, the `Receipt` as issued is stored under the key, whatever the member outcomes, and an identical retry returns that receipt unchanged, including its `observed_at` and `source_valid_until` (v0.5.4): the carrier's clock never makes a stored receipt look newer. Every allocated outcome (owner effect or owner refusal) carries an owner-issued `operation_ref`; refusals before the owner step carry `operation_ref: null`. A member whose owner response was lost is reported `UNKNOWN_EFFECT` with its `operation_ref`; an identical retry reports that same operation from the owner's own record and never dispatches again. That reconciled receipt is a new observation and says so (`carrier_state` is no longer `RECONCILING`); its `observed_at` is the latest of the stored receipt's and the reconciled owner records', and its `source_valid_until` the earliest, so its clock comes only from owner evidence. A newer owner observation of an existing operation is read from the owner (`GET /o01/v0/owner-operations/{operation_ref}`, OP-08), which carries the owner's own `observed_at` and source epoch; the carrier's replay never refreshes it. A `HELD` result allocates nothing (A-24 SW-06) and is stored like any other, so an identical retry returns `HELD` until the stored receipt expires and then `409 unresolved_no_redispatch`; progress needs a new key and, for a protected action, a new consent.
- **CS-09 Receipt conformance.** Every emitted receipt satisfies the SW-06 rules checked by `command_admission.receipt_errors`: results in request order and complete; `ADMITTED` has an `operation_ref`; owner-qualified operation identities are unique; no effect without admission; a confirmed effect has owner evidence; `UNKNOWN_EFFECT`/`PARTIAL` never claims `NONE_QUALIFIED` residual; held or received results carry no `operation_ref`. Checked against a time (v0.5.4), a receipt is current only if it was observed no later than that time and is valid after it (A-24 `RECEIPT_INVALID_CURRENTNESS`; an unreadable clock is `CURRENTNESS_INVALID`).

**Synthetic oracle limits.** The test worlds hold owner-native records only (no copies of expected response stamps): owner records, per-owner source metadata, G3 consent records and HEB/ADC observations. They are independently supplied W0 fixture records, not runtime certification or production signatures. W1–W5 and G1–G4 qualification remain separate. The functional first preview continues using its permitted CLI execution path when G3 is unavailable; no new functional protected-delegation class is introduced.
