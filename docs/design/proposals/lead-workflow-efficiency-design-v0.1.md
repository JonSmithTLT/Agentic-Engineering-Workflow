# Lead workflow efficiency: fewer model steps per Ticket

**Status:** design proposal for the operator and designer, 2026-09-29; superseded by the governing [typed Lead surface v0.2](../typed-lead-surface-design-v0.2.md) (2026-10-05): its stage commands and façade are that design's catalog and runner (ledger LWE-01, LWE-02 absorbed), its pilot order that design's §11 sequencing (LWE-04); its savings target and ceiling stay the evaluation's (LWE-03, F19). No state-machine or product-code change is implied by this document. It follows the M3 [read-only audit](../../archive/reviews/m3-audit-findings.md) and [dogfood report](../../archive/milestones/m3-dogfood-report.md).

## The cost to remove

The audit's 26 hardened AEW runs contain 29 Lead sessions. The median session used 34 model/tool steps, including 20 workflow-command steps, 6 reads, and 4 `harness wait` calls; runs averaged 1.15 Tickets. Thus “20 steps per Ticket” is a useful shorthand, but **20 is a per-session median**, not a measured per-Ticket constant. The Lead was about 40% of AEW's total cost in the dogfood. Waiting consumed wall time; workflow choreography consumed model steps and repeatedly read a growing context.

I re-counted the recorded command *prefixes* in those 29 sessions: 114 `work transition`, 85 `invoke create`, 58 `verify ingest`, 47 `review ingest`, and 100 `status` calls. These are not success counts: the command log lacks the `aew` exit code, and some calls were refusals or retries. They identify the interface's hotspots. A successful single-Ticket T1 run still called create, propose, accept, assign, four waits, three separately logged transitions, two role dispatches, review and verification ingests, prepare, post-integration dispatch, post-integration ingest, and publish, as well as setup and status calls.

The [Knowledge Contract](../../aew-knowledge-contract-v0.4.md#10-work-creation-command-contract) permits convenience aliases if they preserve the durable Ticket semantics. It also requires Lead ownership of plan acceptance, evidence ingestion, failure classification, and integration; atomic, stale-writer-resistant control updates; and reconstructible consequential transitions. [ADR-0003](../../implementation/adr/0003-ticket-state-machine.md) restricts *which operation* may move each state. Neither requires a fresh model reasoning step between every deterministic operation. The opportunity is to make one Lead judgment trigger a guarded sequence of existing engine operations.

## Recommended shape: explicit stage commands

Give the Lead commands named for the judgment it is making. Each command accepts a Ticket ID, `--expect-rev`, and explicit evidence IDs where evidence is being accepted. It performs only the named path, checks the same gates as today's commands, and returns the full sequence of durable outcomes. `--launch` retains the M3 custody path. It never takes a generic “advance until done” instruction.

| Lead intent, after inspecting the relevant material | Current calls on a clean Class 1 path | Candidate one-call stage | Conditions and stop behavior |
|---|---|---|---|
| Draft a Ticket and its proposed plan | `work create`; `plan propose` | `aew ticket draft --intent-file ... --plan-file ...` | Writes the Ticket objective/body and proposed plan as separate existing artifacts. Does **not** accept the plan. F14 later adds its richer raw-intent and assurance rules before acceptance/dispatch. |
| Start work on an accepted, READY Ticket | `work assign --launch`; `work transition --to RUNNING` | `aew ticket start T --launch` | Assign and launch through existing guards. Move to RUNNING only after launch custody is acknowledged. If launch fails, leave the durable ASSIGNED attempt visible. |
| Submit the implementation for independent review | `work transition --to REVIEW_PENDING`; `invoke create --role reviewer --launch` | `aew ticket request-review T --launch` | Require a current implementation report and checks. Choose the review card(s) from the effective role plan; return every invocation and run ID. If no review gate applies, report the appropriate next stage instead. |
| Accept inspected passing review evidence and request verification | `review ingest --evidence E`; `work transition --to VERIFY_PENDING`; `invoke create --role verifier --launch` | `aew ticket request-verification T --review-evidence E --launch` | Ingest only the named report. Continue only when every required review is current, passed, and free of open required findings. A failing or still-pending review stops with that state and no verifier. |
| Accept inspected passing Ticket verification and prepare an integration candidate | `verify ingest --evidence E`; `work transition --to COMMIT_READY`; `integrate prepare`; `invoke create --scope integration --launch` | `aew ticket prepare T --verification E --launch` | Continue only if every required Ticket verifier has passed and all effective gates are current. Stop and report a verification failure, pending card, stale snapshot, merge conflict, or preparation failure at the point it occurs. Launch the post-integration verifier only for a prepared candidate when policy requires one. |
| Publish the integrated result | `verify ingest` (integration); `integrate publish` | Keep an explicit `integrate publish` decision initially | Publication is a ref CAS and has crash-reconciliation semantics. Keep the final Lead decision visible while validating the earlier bundles. The preceding ingest response should supply the revision, candidate, and exact publish command. |

These names are illustrative. The key distinction is **the Lead chooses the stage and evidence**; the engine performs the predictable mechanics inside it. Failure paths remain explicit. `verify classify` must stay a separate Lead judgment after failure; a review with blockers must not trigger verification; interruption and rework must never infer success. Class 0 can lower gates only through a separately justified policy decision. No stage command should silently downgrade risk or bypass the future F14 `ASSURED` predicate at dispatch.

## Implementation path with limited state-machine risk

First build a thin, deterministic CLI/engine façade over the **existing guarded public operations**. It receives the caller's expected revision, uses each successful operation's returned revision for the next operation, and stops on the first refusal. Every underlying transition remains in the durable history with its current `via`; every substep still checks current Lead authority and generation. A bundle is **one Lead tool call, not a claim of one atomic control commit**. Its result should include `completed_steps`, `current_revision`, `work_state`, `runs`, `evidence_accepted`, and `next_action`. On partial completion, the Lead can resume from durable state without repeating a side effect. A retry must identify which substeps already completed, especially after `integrate prepare`; it must never blindly re-run a Git commit or merge. If that is too hard to make unambiguous, keep `prepare` as a separate call in the first release.

Existing CLI `_dispatch` and `launch_dispatched` already combine dispatch, run recording, and custody handoff. Reuse them. Do not add a second path that prints invocation credentials into the model context. An eventual transaction-level refactor may make some pairs atomic, but it is not required to test whether fewer Lead model steps improve outcomes.

For every mutation, return compact structured guidance for the affected Ticket: the new revision, state, unmet gates, submitted-but-not-ingested evidence IDs, and one runnable next command or a named decision required from the Lead. `resume` already computes much of this, but its present `next_actions` are prose strings; they should not be parsed as an execution plan. A typed next-action projection could serve `status`, `resume`, and command results. `harness wait` should return evidence IDs and the relevant revision/next command, reducing routine `status` reads. Keep `--expect-rev` as a real CAS: a stale result must stop the bundle rather than silently fetching a newer revision and continuing.

## Expected savings and ceiling

The first five clean-path rows combine 13 lower-level Lead calls into 5 stage calls, saving **up to 8 lower-level calls**. The final integration-verification ingest and publish remain two explicit calls. Some Leads already chain commands inside one shell step, so the reduction in *model steps* will be smaller and must be measured. A testable target is at least a 25% reduction in workflow-command steps on matched single-Ticket runs; if the session mix remains comparable, that would move the observed 20-step median toward **15**. The number of independent reviews and verifications stays fixed. A cleaner response may remove another one or two reads. These are targets, not observed outcomes.

Even a large Lead saving will not remove the cost of implementer, reviewer, verifier, and post-integration verifier runs. With the Lead at about 40% of AEW cost, halving only the Lead's cost would cap total cost savings near 20% before any interaction effects. Reducing the reported ~7× AEW/raw gap further requires separate choices about role policy, model routing, and task success. The first efficiency measure should be **successful work per dollar and minute**, not command count alone.

## Pilot and acceptance test

1. Instrument the command log with actual `aew` exit code, error code, revision before/after, and stage substeps; retain token and cost accounting. This fixes the current ambiguity in refusal counts.
2. Implement only `draft`, `start`, and `request-review` behind an opt-in CLI path. Use existing M1/M2/M3 acceptance scenarios unchanged, then add focused tests for stale revision, failed launch, missing or stale report, extra required review card, handoff/interruption, and a retry after partial completion.
3. Extend to `request-verification` and `prepare` only after the first three preserve the current invariants. A failing report must be ingested and leave the exact failure state; no subsequent role may launch. A merge conflict must leave a reconstructible candidate disposition.
4. Replay paired clean, rejection/rework, and interrupted Ticket tasks with the same model/profile, workload, and gate policy. Report Lead steps and cached input tokens, Lead and total cost, wall time, task success, refusals, and any false advance. Compare the M3 dogfood baseline without reclassifying tasks to Class 0.

**Timing and decision:** keep this as a design proposal through M3 independent review. Pilot stage commands after the review, with low-level commands retained for recovery and unusual paths. The designer should decide whether the stage commands become the primary Lead interface. The proposed first pilot appears consistent with the existing Workflow Contract because it composes guarded transitions while preserving their individual durable records; any plan to auto-accept evidence, auto-classify a failure, or auto-publish would need a separate design decision and contract review.
