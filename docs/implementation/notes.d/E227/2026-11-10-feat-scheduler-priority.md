**Built (`feat/scheduler-priority`), the scheduler chain's second PR (E228).** A Ticket's priority is `critical`, `normal` (the default) or `low`, with a reason, set at the draft only: `ticket_draft`'s `priority` and `priority_reason`, or `aew work create --priority --priority-reason`. The operator, 2026-11-10: it is "not a field that would cause us to have to throw a ticket away if its wrong", so it is fixed for now; changing it later is a row of its own, which the Lead files.
- **The levels' owner** is the control schema (`work_unit.priority.level`), read in one engine-free module, `aew.priority_levels`. `aew.engine.priority`, the CLI's parser and the Lead's tool all take them from there, so the `aew lead mcp` process, which builds the parser and then the transport, loads no engine module; its pin now probes that path.
- **A `critical` or `low` priority needs a reason.** A priority on a Story or Epic is refused. Setting one is a draft, so it stays the Lead's judgment and is never auto-run.
- **The loop's `select`** takes Tickets by level, then by how many live Tickets each unblocks (Tickets with an effective dependency edge on it, own or inherited, derived each tick; Stories and Epics are not counted, so an edge to a Story credits none of its Tickets), then by id. A `low` Ticket starts only when no `critical` or `normal` one is eligible. Nothing is pre-empted. With none eligible, the stop reported is the first in that order, so a higher Ticket's self-clearing BLOCKED can be reported in place of a lower one's Lead decision (stated in `select`; the `loop_waiting` PR ranks the Lead-only stops first). Starting a Ticket stays `ticket_start`, CAS-checked as before, so the loop and the Lead can't double-start one: E227 needed no new tool name (E231).
- **`status`** shows a priority that isn't the default beside its Ticket, with its reason, and the age of a `low` Ticket that has not started (READY or BLOCKED). The generated `CURRENT.md` shows the level and reason but no age, so it stays a function of the state. The status report's `work` entry carries `priority` only when it isn't the default.
- **The Ticket field registry, v1 in place** (ADR-0016 §1.5, A-47: before S3 binds evidence, a new group goes into version 1): a non-material `scheduling` group holds `control:priority`. Every other group's digest is unchanged, and a priority never stales a Ticket's evidence.
