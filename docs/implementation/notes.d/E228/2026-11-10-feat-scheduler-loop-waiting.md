**Built (`feat/scheduler-loop-waiting`), the chain's first PR: A-58 `CL-R07`'s `loop_waiting`, which was marked not yet produced.** It is a reason in the one wake list (`contract.WAKE_GUIDE`), for a steering loop stop that waits on the Lead's judgment.
- **Which stops:** every stop the loop records in `loop.json` but idle. That covers `DECISION_REQUIRED`, `BLOCKED` and `UNKNOWN`, which were recorded and never notified, and the attention stops, which notified only the operator. Steering off records nothing, so it never wakes. With nothing eligible, the loop reports a stop only the Lead can clear (`DECISION_REQUIRED`, `UNKNOWN`) ahead of a BLOCKED that can clear on its own, so the wake names what needs the Lead.
- **The run-less slot:** the wake's own `loop` entry beside `runs`, holding the stop's code, subject and message. The wake's text adds one line of the loop's own values; the message stays in the JSON, as data. The message is redacted before each cut (when recorded, and in `loop_state`), so no credential's fragment survives a cut.
- **Still holds:** when the post is due, `loop.json` still shows the same occurrence of the stop for the current Lead generation. A Lead call does not clear it: only `status` and the steering view show the loop's stop, so a stop that arose during the Lead's turn would be lost after its next call (the review's M1, the Lead's ruling of 2026-11-10 changing the brief's rule). A wake that fails the check is dropped and counted.
- **Told once:** per occurrence, keyed by the generation, the stop's condition (`steering_loop.condition_key`) and the loop's occurrence number. The loop writes the number into `loop.json` from its own last record, so a restarted broker in the same generation keeps it: the same while the condition is the same and the loop has acted on nothing about the stop since (its subject, or anything for a `project` stop), else one more. An action on another subject never moves it, so a busy activation doesn't re-tell a stuck Ticket's stop, which is the re-arming `CL-B1`'s fourth bullet warns of. The limit: a different stop recorded in between moves it too, so the Lead is told the same stop again then (one more wake, never a missed one). The occurrence is marked told by the wake that told it, so that wake re-posted to a new session that never saw it keeps its stop. `BOY-09` still stands beside it, on its own clock, for the operator.
- **A run the loop ingests:** under Run, the loop auto-runs `ticket_request_review` on a Ticket whose implementer reported, and that transition's guard ingests the implementer's run. So a `run_ended` whose Ticket the loop will advance that way isn't current (`SteeringLoop.will_ingest`): it doesn't wake, and if the step stops, the loop's own stop does. Which guards ingest is `Gates.INGESTS_IMPLEMENTATION`, and a test derives it from the guards' code, so a guard that starts ingesting moves it. `test_failed` and `out_of_scope` wake as before.
- **What the Lead is told:** the push-only rows of its system text (`lead_wake_text`) now come from `contract.PUSHED_ONLY` (`quiet`, `loop_waiting`), not from a hand-written row. The guide says the loop won't act on the stop's subject until the Lead does; other Tickets' steps go on.
