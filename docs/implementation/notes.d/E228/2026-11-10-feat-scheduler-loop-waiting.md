**Built (`feat/scheduler-loop-waiting`), the chain's first PR: A-58 `CL-R07`'s `loop_waiting`, which was marked not yet produced.** It is a reason in the one wake list (`contract.WAKE_GUIDE`), for a steering loop stop that waits on the Lead's judgment.
- **Which stops:** every stop the loop records in `loop.json` but idle. That covers `DECISION_REQUIRED`, `BLOCKED` and `UNKNOWN`, which were recorded and never notified because the Lead's next call would see them, and the attention stops, which notified only the operator. Steering off records nothing, so it never wakes.
- **The run-less slot:** the wake's own `loop` entry beside `runs`, holding the stop's code, subject and message. The wake's text adds one line of the loop's own values; the message stays in the JSON, as data.
- **Still holds:** when the post is due, `loop.json` still shows a stop with the same condition, for the current Lead generation, and the Lead hasn't called its broker since the queue first saw the stop. That is `BOY-09.b`'s own clear: the Lead's next call shows it the stop. A wake that fails the check is dropped and counted.
- **Told once:** per occurrence, keyed by the generation and the stop's condition (`Stop.condition`, written to `loop.json` as `steering_loop.condition_key`). The Lead's last call is deliberately not part of the key. A Lead that is woken, reads and ends its turn is not woken again for the same stop, which is the re-arming `CL-B1`'s fourth bullet warns of. The loop moving past the stop and stopping there again is a new occurrence. `BOY-09` still stands beside it, on its own clock, for the operator.
- **A run the loop ingests:** the loop auto-runs only steps that aren't judgment-bearing, and none of them ingests a run today. So every run's end is still the Lead's news, and `run_ended` keeps waking. A test fails the day an auto-run step ingests, so that step must make the queue drop such a run's end. `test_failed` and `out_of_scope` wake as before.
- **What the Lead is told:** the push-only rows of its system text (`lead_wake_text`) now come from `contract.PUSHED_ONLY` (`quiet`, `loop_waiting`), not from a hand-written row.
- **Last call:** the broker records when the Lead last called it (any op), and the queue reads that. A broker that starts again knows no last call, so the worst case is one more wake, as the queue already accepts.
