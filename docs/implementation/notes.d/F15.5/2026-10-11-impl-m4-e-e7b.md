**Built (M4-E E7b, the steering loop; [plan v3](../../m4-e-plan-v3.md) E7 as split by [its amendment 1](../../m4-e-plan-v3-amendment-1.md)).** The loop (`harness/steering_loop.py`) runs in the Lead broker on its own thread and an engine of its own, woken by a committed Lead tool call and by a commit or a run record it sees within `POLL_S`, and, because a run record's wake is advisory (on Windows a bump fails while another handle is open on the wake file, which `outbox.bump_wake` now retries briefly), by a coarse look every `COARSE_S` that starts an activation only when the projection would select something other than the last tick did, so a look never restarts the envelope; with no steering mode it does nothing and writes nothing. Each tick reads the project's and every live Ticket's projection and stops for the same reasons in every mode (CWR §2, §11): stale authority or policy, an open high anomaly anywhere, a project-level blocker or decision; a Ticket with a decision, a blocker or an UNKNOWN action is never advanced, and nothing that is not AVAILABLE and `auto_runnable` ever runs. `confirm_before` (`steering.confirmation_reason`): Crawl always; Walk unless every primitive's declared side effects are in `{control_state}`, failing closed on an undeclared primitive, no class, an unknown class or no primitives (A1 §2); Run never. There is no confirmation yet (amendment 1, m3): such an action is never executed and the loop stops with `CONFIRMATION_UNAVAILABLE`, which M4-E E7c replaces.

The envelope (`execution.steering.envelope`: `loop_deadline_s` 3,600, `max_auto_actions` 50, `repetition_n` 2; operational) bounds each activation, and an activation woken only by the loop's own last commits resumes the one before it, so the envelope is never restarted by the loop itself. The repetition key is the action, its arguments without `expect_rev`, the subject and its state, counted from the last commit the loop did not make. In Run, at each activation, the notifier must be executable and the operator endpoint must answer (`NOTIFIER_UNAVAILABLE`), and a dispatching action needs `deadline_s` on every profile routing can pick (`NO_HARD_DEADLINE`). An action runs as a normal stage call with the projection's `expect_rev` and a StageIntent whose new optional `auto_run` field attributes it (the activation, the mode with its record and generation, both digests, the projection); its dispatches carry channel `steering_loop`. Each step's own commit is then held to its primitives' declarations by its typed events (SAE-07 at runtime), every event kind mapped to the classes it shows: an excess opens a high `SIDE_EFFECT_UNDECLARED` anomaly and stops the loop, and a commit that cannot be read with its events, or carries a kind no class maps, stops it with attention (`DECLARATION_UNCHECKED`), never passed. A run its supervisor ends at its hard deadline leaves a signal that the next Lead commit records as a low `HARD_DEADLINE` anomaly; nothing is advanced, released or relaunched.

The loop's state is `.aew/local/steering/loop.json`, shown in `status`. A stop that needs attention appends `loop_stopped` to the broker's event spool once per condition (the code, the subject and the action with its arguments, never the revision; kept across quiet stops), and the operator endpoint notifies it, as it now notifies `anomaly_high`. Only what a tick has read counts as seen, so a change after the last read is acted on; once the broker starts closing, no new action starts. A loop whose generation has been superseded writes nothing shared and notifies nothing (the takeover is the endpoint's `generation_ended`); `loop.json` carries its generation, and `status` shows only the current one's. A mode change never interrupts an executing action: a stage R5-1 can re-ask completes, its next step retried once, with its binding unchanged and nothing STALE_POLICY.
