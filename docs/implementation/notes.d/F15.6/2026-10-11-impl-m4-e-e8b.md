**R5-3 built (M4-E E8b; [plan v3](../../m4-e-plan-v3.md) E8 and N2c, as split by [its amendment 1](../../m4-e-plan-v3-amendment-1.md)).** `engine/recovery.py`. Off by default: `execution.recovery.relaunch_launch_failed` is 0 unless the operator adopts 1, and every other `recovery:` key is refused by the schema (BRP-08). The setting and the breaker's bounds (`breaker.threshold`, default 3; `breaker.window_s`, default 300) are operational, snapshotted at each recovery decision; a change adopted before the relaunch commits re-evaluates that pending recovery inside the relaunch's transaction and never stales anything else (A3 §5).

**Where (N2c).** Only the stage runner relaunches, at a stage's `launch_failed` stop, under the broker's Lead credential (`surface/stage.py`, `_recover`; a static test pins the one caller). `aew harness launch`, `--launch` on the CLI and the recovery `cli` escape never reach it. The supervisor only observes: at a failed start it adds its observations to the acknowledgement on its pipe (and, as telemetry, to the run record): the record ended, the process tree empty (Windows: the job object's count; POSIX: the process group), every process it started gone (the harness server among them), the POSIX sentinel released, whether the task prompt was delivered (the adapter's new `prompt_delivered`: False until it sends, None from the POST on, so a failure that may follow a delivered prompt is never relaunched), and how many requests reached the bridge. The launcher adds that the supervisor process exited.

**Eligibility, all required.** The reason code comes only from the supervisor's acknowledgement or the launcher's own value (`reason_code_source`); any other source, a code in the model-writable run directory included, is `unknown` (amendment 1, R2-m2 and R3-n1). The code is on the recovery module's own allow-list (`spawn_race`, `server_start_transport`), the invocation is active, the failed run is its latest and holds its credential, its dispatch decision, base binding, legality digest, Ticket state and attempt are those bound at the failure, no blocked report, unresolved finding, open anomaly or required disposition exists for the Ticket, and it is the invocation's first relaunch. The termination proof needs every observation this platform's rule names to be true (Linux: record, tree, processes, sentinel, supervisor exit; Windows: record, job object, processes, supervisor exit; any other platform has no rule and is ineligible). The no-side-effect proof reads the run log and the bridge (no request), the network (the prompt recorded as never delivered), the evidence store (nothing from the run), and the workspace fingerprint and HEAD against the dispatch's `snapshot`. Anything unobservable is ineligible; the stage then stops at `launch_failed` as before, with the verdict (each unmet condition, by code) on its error's `recovery` detail.

**The relaunch** is one Lead transaction under a new `harness.launch` decision: the failed run's credential is revoked, the revocation confirmed through `run_authority_problem`, and only then a credential minted for the new run id (A2 §3). The invocation's `relaunch` record binds the failed and new runs, both proofs, the revocation, the code and its source, the breaker's state, the policy snapshot and the stage intent (A2 §7); both runs stay in `runs[]`, and the stage goes on over the new run. A second failure stops the stage at `launch_failed` with `second_failure` on its `recovery` detail, and nothing more is relaunched. **The breaker** (control state `recovery.breakers`, per `<harness>:<provider>`, or `project` for `spawn_race`, a cause shared by every harness on the host): an eligible failure is counted, the one that reaches the threshold opens it and is not relaunched, and an open scope refuses relaunch until `aew recovery breaker reset` at the operator endpoint (`relaunch_breaker_reset`, the peer check and the challenge, closing exactly the scopes shown). `aew recovery breaker status` reads it.

**No real failure reaches the allow-list yet.** E8a maps a failure only where a test reproduces it (`credential_denied`, `incompatible_config`), so in production every relaunch verdict is ineligible until a real failure is mapped to `spawn_race` or `server_start_transport` with the test that reproduces it. The tests seed the allow-listed code where it really comes from: the supervisor's acknowledgement, rewritten on the launcher's side of the pipe in the test process. On Linux the proof reads the plan's first alternative, the process group, and not a count of the bwrap PID namespace: bwrap and the sandbox it starts stay in the run's group (no `--new-session`), and every process the tree started must be gone too.
