**G3-D, the CLI client (2026-10-25), built from A-37 (G3 revision 7.1), the designer's hand-off and the Lead's three
rulings on it.** `aew g3 request <set.json> --o01 <url> --token-file <file>`, in `src/aew/g3client.py` and
`src/aew/cli/g3_commands.py`. What it is:
- **The set (ruling 1):** a complete O-01 0.2 `CommandSet` from a JSON file. A set that carries `origin_proof_ref` or
  `consent_set_ref`, or any member that is not a protected action, is refused before anything is sent, each refusal
  naming the fix. A typed builder per action comes with that action's wiring, not here.
- **The approval (G3-02, G3-07):** a fresh proof per member from `secrets`, the set submitted on `request.sock`, then
  the approval asked after every second until it is decided, expires, or is lost to a restart, bounded by its own
  expiry and the deployment's ten-minute ceiling. The client never sees a PIN. Before submitting, it checks that the
  record's `set_digest` is the SW-02 digest of the set it will send.
- **The submission (ruling 2):** over the STG-02 route `POST /o01/v0/command-sets`, on the loopback only, never the
  carrier in process. The bearer token comes from a file, and is never printed, logged or put in an error. The receipt
  is printed; while G3-C has not landed, its `ORIGIN_NOT_ESTABLISHED` carries a fixed note that G3 is not yet
  established on this host and what establishes it. Today the route answers a protected set with consent `REJECTED`
  with that reason, not `HELD`.
- **The home (ruling 3):** the operator's, `forbidden-to-lead`, kept out today by the CLI's Lead-session refusal, now
  one function (`custody_ops.refuse_in_lead_session`) that `aew capability` shares. CS-4's containment becomes the
  second keep-out in its surface-map entry when CS-4 merges (in G3-C, or here if CS-4 merges first). A Lead
  requesting an operator approval is not built.
- **The tests:** `tests/unit/test_g3client.py` (both platforms) and `tests/integration/test_g3client_process.py`
  (Linux, against the real service and the STG-02 route).
- **#282's quick-check follow-ons** (Q1, Q2, Q3, N1) are fixed in this branch.
- **The confirmer, from the operator's first run of the install:** a launch from a terminal says where its window
  is, and one with no display reachable says so, naming the route, and exits 3. A static test holds that every
  `confirm.sock` call runs off GTK's main loop, as it has since #282. The desktop freeze reported on that run is
  being separated from the VM's own pointer handling by the operator's next step, and nothing in the confirmer is
  changed for it.
