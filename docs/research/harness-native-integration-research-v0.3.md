# T9 — Harness-native integration strategy: OpenCode and Codex under the frozen AEW boundary (v0.3)

- **Status:** **research complete / implementation input accepted**, 2026-10-04. This v0.3 folds in both final live probes: OpenCode 2.0.18 request-level behavior and Codex CLI 0.160.0 app-server behavior. It remains a versioned research/design input rather than a permanent harness contract; support claims are per adapter + pinned version + schema/probe identity.
- **Question:** given the frozen typed AEW action surface (T1) and the engine's authority over legality, which native capabilities of OpenCode and Codex should AEW exploit for execution, UX, context economy, containment, observability or reliability, without creating a second authority path?
- **Evidence classes used in this note, marked in every row:** **[doc]** current primary documentation read 2026-10-04 (OpenCode: `opencode.ai/docs/{mcp-servers,agents,permissions,plugins,server,sdk,skills,config,rules,tools,custom-tools,cli}`; Codex: `learn.chatgpt.com/docs/{app-server,config-file/config-reference,agent-approvals-security,hooks,non-interactive-mode,extend/mcp,build-skills,agent-configuration/subagents,cli/reference}`, the new home of `developers.openai.com/codex/*`, which redirects there); **[pin]** the OpenCode 2.0.18 OpenAPI pinned in `tests/fixtures/opencode/openapi-2.0.18.min.json` (17 paths; `Config.InfoEncoded`, `Permission.Rule`, `Mcp.LocalConfigEncoded`, `Mcp.Protocol`); **[probe]** run in this review (OpenCode 2.0.18 request capture and real MCP spawn; Codex CLI 0.160.0 app-server handshake/schema/MCP inventory/request capture; T6 network/startup/proxy probes on Rocky 8.10); **[inf]** architectural inference; **[rec]** recommendation; **[hyp]** unresolved hypothesis that needs a live probe.
- **Not reopened:** T1 (actions and stages below transport; MCP as the first Lead transport; CLI parity; broker custody), ADR-0009 (the narrow adapter; nothing an adapter reports is evidence), ADR-0011, ADR-0012, `DispatchDecision`, M4-B containment labels.

## 0. The one finding that frames the rest

**The pinned OpenCode 2.0.18 API and the public OpenCode documentation describe different products.** [pin] exposes `/api/session`, `/api/event`, `/api/model`, `/api/agent`, `/api/info`, permissions as `Permission.Rule {action, resource, effect}` rulesets, MCP as `mcp.servers.<name> {type, command, protocol}` with `Mcp.Protocol` `legacy | auto | 2026-07-28`, config keys `agents`, `permissions`, `plugins`, `skills`, `tool_output {max_bytes, max_lines}`, `compaction {auto, buffer, keep}`. [doc] describes `/session`, `/global/event`, `/mcp`, `permission: {read, edit, bash, task, skill, …}` objects, `mcp.<name> {type, command, enabled}`, `tools`, `plugin`, `compaction {auto, prune, reserved}`. The capability probe (`harness/opencode/capabilities.py`) exists because of exactly this: "V2 publishes no stability policy and labels its HTTP API experimental". Codex is more explicit: the app-server is labelled experimental in the CLI reference, `codex mcp-server` was removed in favour of it, and the configuration reference marks a dozen features experimental.

Consequence for every row below: **"documented" means documented for some version; what AEW may rely on is what the pinned binary's own schema advertises**, checked at launch, which is the discipline the adapter already applies and which a Codex adapter must copy (app-server has `generate-json-schema` for exactly this). The registry representation (F13) therefore records capabilities **per adapter per pinned version**, never per product.

The first live OpenCode request probe reinforces that rule rather than weakening it. On 2.0.18, one pinned config flag (`mcp.servers.<name>.codemode: false`) changes whether AEW appears as twelve ordinary function tools or only as a Code Mode namespace reachable through `execute`; per-agent `deny` rules also remove denied tool schemas from the actual model request. These are pin-specific observed facts, not product-wide assumptions.

The second live probe establishes the same lesson from the other direction. Codex CLI 0.160.0 exposes a healthy MCP server and filtered MCP inventory through the app-server, but the model request does **not** receive those MCP tools as ordinary function tools: they remain deferred behind Codex's `exec`/Code Mode runtime. The same request also carried sub-agent tools and a bundled system skill despite the disable flags tried. A generated app-server schema is therefore necessary but not sufficient for an AEW support claim; the real model-visible request surface is part of per-pin conformance.

## B. Recommended integration profile

### OpenCode (pinned 2.0.18, next pin to be chosen by probe)

- **MUST USE:** one private `serve --stdio` per run inside the supervisor's tree; the capability probe against the served `/openapi.json`; `OPENCODE_CONFIG_CONTENT` projection with `OPENCODE_DISABLE_PROJECT_CONFIG`; session environment replacement; `Permission.Rule` allow/deny only; model and variant pins verified against `/api/model`; `tool_output {max_bytes, max_lines}`; the event stream for telemetry; `mcp.servers.aew` for the Lead (T1) with **`codemode: false` on pinned 2.0.18**, because the live probe shows the default otherwise routes AEW through Code Mode instead of exposing the twelve typed tools directly.
- **SHOULD USE:** per-agent tool filtering (`agents.<n>.permissions`/`tools`) to hide every tool a role does not need; **the 2.0.18 request-level probe now proves denied schemas leave the request**; a run-private `.agents/skills` directory with the curated skills a card requests (D3, U9), disclosed by the native `skill` tool; the `/api/session/{id}/environment` route for the curated environment (already); `interrupt` and inbox delivery (already).
- **OPTIONAL:** `compaction` tuning after measurement; `opencode attach` for a second operator view; the `question` tool for the Lead only (never for runs).
- **DELIBERATELY DO NOT USE:** `ask` permissions in runs; `task`/subagents (until F13's grant); project plugins and `.opencode/` directories in runs; session resume as AEW recovery; `share`; `autoupdate`; LSP and formatter in runs (already off; both fetch and write); the remote `.well-known/opencode` configuration layer. `execute` and the inherited desktop `browser` namespace are **explicitly denied in worker runs** and covered by conformance, rather than merely inherited from a broad rule set.
- **NEEDS LIVE PROBE:** whether `OPENCODE_DISABLE_PROJECT_CONFIG` covers `.opencode/plugins` and the `.well-known` fetch; the plugin API's `experimental.session.compacting` presence in the pinned version; the catalog behaviour with a configured provider and no network (T6 part 3). **Tool-filter schema removal is closed for 2.0.18.**

### Codex (probed pin: CLI 0.160.0 / app-server protocol v2)

- **TRANSPORT VIABLE:** the app-server itself is a workable private adapter transport. Stdio initialization, thread lifecycle, interrupt, effective sandbox reporting, MCP startup state and generated JSON schema all behaved cleanly on Rocky 8.10.
- **NOT YET SUPPORT-READY AS AN AEW HARNESS PIN:** on 0.160.0, ordinary MCP configuration does not present the T1 AEW catalog as direct model function tools. MCP is deferred behind Codex's JavaScript `exec` runtime. The same captured request carried recursive sub-agent tools/instructions and a bundled system skill/base prompt that AEW did not request.
- **MUST USE once a Codex pin qualifies:** one private app-server per run under the supervisor; pinned generated protocol schema/hash; private `CODEX_HOME`; `--ignore-user-config --ignore-rules`; `shell_environment_policy.inherit = none`; `approval_policy = never` for runs; explicit effective-policy verification; loud MCP readiness/failure via `mcpServerStatus/list`/notifications; telemetry and interrupt.
- **SUPPORT-BLOCKING QUALIFICATION:** demonstrate a direct typed Lead action presentation (`DynamicToolSpec`/client registration or a newer pin with equivalent semantics) without routing T1 through generic JS `exec`; prove native collaboration/subagent tools/instructions are absent unless F13 explicitly grants them; disable/replace bundled system skills and ambient base instructions; pass custody and "nothing else loaded" conformance.
- **OPTIONAL AFTER SUPPORT:** native sandbox as defence in depth if nested-bwrap composition is proven; `enabled_tools` inventory narrowing; output schemas for F19 raw arms; curated skills if evaluation earns them; Unix-socket transport if T6 deployment needs it.
- **DELIBERATELY DO NOT USE:** generic Code Mode as the normal T1 Lead transport; uncontrolled `collaboration`/multi-agent facilities; harness approvals as AEW decisions; shared login state; decision-making hooks; memories; session resume as AEW recovery.

The consequence is intentionally conservative: **Codex is still a promising adapter target, but CLI 0.160.0 is evidence for the capability registry, not a supported AEW pin.** No architecture needs reopening; an implementation spike later either finds the direct registration seam or selects a pin that exposes it.

## D. Initial support target: what "AEW supports OpenCode / Codex" means

**Minimum conformance (both):** the harness-neutral scenarios of `harness-conformance.md` §2 pass against the real binary (the live lane), plus the acceptance scenarios AT-14..AT-17; the capability probe against the pinned schema fails closed on any gap; the custody properties hold (no credential, provider key or server secret in any model-controlled process or file); allow/deny only; private instance per run; effective model equals the pin; `stopping_a_run_ends_every_process_it_started` passes on Linux under the M4-B layout; the new "nothing else loaded" scenario passes. For the Lead, **AEW MCP readiness is explicit**: a missing/failed server cannot silently degrade into a session without the AEW control surface.

**Optional enhanced capabilities (declared per pin, never assumed):** request-level schema filtering where measured; curated native skills after evaluation; native sandbox as a second line; output limits/schemas; alternate transports. Codex 0.160.0 `enabled_tools` is inventory narrowing only, not a demonstrated context-reduction feature.

**Degraded but correct:** a harness without a capability runs with the fallback column of the matrix and the run label says so (the F13 vocabulary `UNSUPPORTED`): no skills → the card's skills are reported unavailable (today's rule); no native sandbox → AEW's layout alone, label unchanged; no `interrupt` → `terminate`; no event stream → polling (already the rule). Nothing degraded changes a gate, a transition or a label's truthfulness.

**Version and protocol compatibility:** one pinned version per adapter at a time (`TESTED_VERSIONS`), with the pinned schema in `tests/fixtures/<harness>/`; a new version is adopted by regenerating the fixture, re-running the live lane, and updating the matrix's evidence column; MCP protocol revisions negotiated (`Mcp.Protocol` on OpenCode; `initialize` on Codex) with the server declaring what it speaks (T1's four revisions).

**Live smoke (per pin, before "supported"):** server start/schema probe; one scripted run through the bridge with evidence ingested; broker-only AEW control-surface readiness; a run under the M4-B layout on Rocky 8.10; the "nothing else loaded" **model-visible request** scenario; cost telemetry. OpenCode 2.0.18 must expose direct function tools with `codemode:false`. A Codex pin must likewise prove the T1 surface is directly usable without generic JS mediation and must prove ungranted collaboration/system-skill surfaces absent.

## E. Live probe 1 integrated: OpenCode 2.0.18 request-level behavior

The first live probe (`T9-live-probe-1-results.md`) ran on Rocky 8.10 against a frozen T1 review checkout and captured the actual Responses API request body at a fake OpenAI-compatible endpoint. No model ran.

Observed:

- baseline Lead request: 9 function tools;
- adding `aew lead mcp` with default Code Mode: server spawned, but no `aew_*` function tools; the instructions gained an `aew` namespace catalog reached through `execute`;
- `codemode: false`: all twelve `aew_*` tools appeared directly;
- the twelve AEW schemas contributed 11,178 request bytes (about 2.8k tokens);
- per-agent `deny` removed denied tool schemas from the actual request;
- run-style `deny *` + explicit allows removed `execute`, Code Mode instructions and the inherited desktop-browser catalog;
- OpenCode 2.0.18 exposes a built-in desktop `browser` namespace through Code Mode whenever `execute` is available;
- an MCP server that fails to start disappears silently from the model-visible surface.

### Custody caveat (probe 1)

The **probe harness** launched `aew lead mcp` in the older prototype's direct-token mode so it could isolate OpenCode request behavior. That setup is evidence about OpenCode's tool exposure/filtering only. It does **not** alter T1's frozen production custody boundary: the production `aew-lead` MCP process is broker-backed and does not hold `AEW_LEAD_TOKEN`.

Any production readiness/smoke test must therefore repeat the server-start/catalog check through the broker-only architecture.

## F. Live probe 2 integrated: Codex CLI 0.160.0 app-server behavior

The final T9 probe ran Codex CLI 0.160.0 on the real Rocky 8.10 VM with a private `CODEX_HOME`, fake Responses endpoint and no model execution.

Observed:

- `codex app-server generate-json-schema` produced a 651-definition v2 protocol fixture candidate;
- stdio `initialize`, `thread/start`, `turn/start` and `turn/interrupt` worked in under a second;
- `mcpServerStatus/list` reported AEW MCP startup, server identity and tool inventory, and gave an explicit failure notification when the MCP server could not authenticate;
- `enabled_tools` narrowed the MCP inventory from 12 tools to 2, but did **not** change the model request;
- AEW MCP tools were not direct model function tools: they were deferred behind Codex's `exec` JavaScript runtime / `ALL_TOOLS` mechanism at roughly 3.6 KB fixed request cost;
- disabling `multi_agent` and `code_mode_host` with the flags tried did not remove the model-visible `collaboration` namespace or recursive-subagent instructions from the request;
- a fresh private Codex home still contributed a bundled `.system` `imagegen` skill, a skills-instructions block and roughly 19 KB of Codex base instructions;
- `thread/start` reported the effective sandbox/approval policy, which is useful telemetry but not AEW authority;
- the release artifact is a signed musl tarball with bundled `bwrap`, `rg`, `codex-code-mode-host` and a layout manifest, which is useful T10 air-gap input.

### Design meaning

The probe **does not reject Codex as an adapter architecture**. It does something more useful: it proves that CLI 0.160.0 is not yet a supportable AEW pin under the normal T1/worker boundaries.

For the Lead, routing a typed AEW action through generic JavaScript `exec` would reintroduce an unnecessary interpretation/execution layer that OpenCode 2.0.18 can avoid. For worker runs, model-visible recursive delegation and unrequested host-bundled skill/instruction material fail the "nothing else loaded" expectation until explicitly suppressed and verified.

Therefore the next Codex implementation work is a **bounded qualification spike**, not another architecture design: try the documented experimental `DynamicToolSpec`/client-registration path (or select a later pin) and identify the supported suppression mechanism for collaboration/system skills. If those conditions can be proven, the same T1/F13 semantics apply unchanged.

### Custody caveat (probe 2)

As with probe 1, the lab forwarded `AEW_LEAD_TOKEN` into the MCP process to isolate harness behavior. That is not the production architecture. Production remains broker-custodied; no final support claim may rely on the direct-token probe setup.

## G. Remaining qualification work, not open architecture

T9 itself is complete. There is no remaining design question that should block moving on.

**OpenCode 2.0.18 support qualification**
- broker-only MCP readiness/catalog smoke;
- prove project/global/plugin/remote config cannot enter worker runs;
- retain request-level "nothing else loaded" conformance.

**Codex future support qualification**
- direct typed-tool registration or a later pin that provides equivalent T1 presentation;
- prove native collaboration/subagent surface is absent unless explicitly granted by F13;
- suppress/replace bundled system skills and ambient base instructions;
- curated-environment/custody and project/user config isolation;
- ordinary live lane / containment / telemetry tests.

**Enhancement-only after support**
- nested native sandbox composition;
- hooks only if a concrete non-authority consumer appears;
- `unix://` transport only if T6 deployment needs it;
- native skills only after evaluation demonstrates value.

These are implementation/conformance tasks. They do not reopen T1, DispatchDecision, custody, AEW recovery semantics or harness-neutral workflow semantics.

## H. Design-authority disposition

**T9 — RESEARCH COMPLETE / IMPLEMENTATION INPUT ACCEPTED.**

Durable conclusions:

1. Harness capability state is keyed by **adapter + pinned version + schema/probe identity**, never by product name alone.
2. Harness-native features may improve execution, context economy, UX or defence in depth, but never become AEW workflow authority.
3. Missing optional native capabilities degrade to the harness-neutral fallback and must not change gates/transitions/evidence semantics.
4. A supported pin requires real-binary conformance, custody, effective-model verification, process/containment checks and a "nothing else loaded" test.
5. OpenCode 2.0.18 specifically requires `codemode: false` for the Lead AEW MCP surface and has measured request-level tool-schema filtering.
6. Codex CLI 0.160.0 has a viable app-server transport and observable MCP readiness, but it is **not a supported AEW pin**: MCP is deferred behind generic `exec`, and the captured model surface still contains ungranted collaboration/subagent and bundled-skill/instruction material.
7. A supported Codex pin must prove direct typed T1 action presentation (or an explicitly equivalent transport) and absence of ungranted model-visible capabilities.
8. A Lead session must fail closed if the AEW control surface is unavailable; silent namespace disappearance is not an acceptable supported state.
9. Harness capability records distinguish **available/inventory** from **model-visible presentation**; configuration intent alone is not a capability guarantee.
10. The capability matrix is a versioned qualification artifact, not a permanent normative contract. Re-run/regenerate it when a harness pin changes.

No further T9 design document or probe is required for architecture closure. F13/Q12, T10 and the adapters consume this note as evidence/input; future Codex work is pin qualification.
