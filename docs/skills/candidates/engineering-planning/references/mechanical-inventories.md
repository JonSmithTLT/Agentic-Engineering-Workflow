# Mechanical inventories for complete-scope claims

Use when a plan claims every occurrence, consumer, route, registry member, or other enumerable class is covered.

Define the class by behavior or structure, its search boundary, and known blind spots. Inspect and retain the search script, exact command, source snapshot, generated output, and content hashes with the plan; commit them through the existing authorized workflow. If commits are unavailable, preserve the files and explicitly report that limitation. Never fabricate a commit or make repository mutation a prerequisite for a read-only plan.

Generate the inventory mechanically. Use the same enumeration method for the planned guard and retained inventory so future additions become visible; separately challenge that method with representative missed forms. A shared search can reproduce a shared blind spot. Decode values or inspect structure where spelling searches miss equivalent constructs.

Give each site an owner and disposition. Exclusions must say what they hide and why; an unmatched site should fail the coverage check. Assert unique identities before building dictionaries. For overlapping plans, join their inventories and resolve duplicate or missing ownership. Bind external behavioral rules to their source locations rather than silently hard-coding them into a table walker.

When a model restates a live registry, compare both missing and extra members, plus contract-relevant fields, against the runtime owner. Membership alone does not prove behavioral equivalence. Do not import application code with unknown side effects merely to enumerate it; inspect first and use a permitted isolated mechanism.

A revised hash-bound companion gets a new identified artifact and updated references. Preserve the earlier bytes when previous evidence depends on them. Report the planned gate's original result before proposing an exclusion or wider scope that changes it.
