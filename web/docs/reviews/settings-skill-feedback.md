# Settings pilot: skill and context feedback

## Skill identity and use

AEW frontend-design candidate 0.2.0, entrypoint SHA-256 `69e52feb459bba5e13c2dbf2ee006f9e8cdd340eb4bf0fafe7080aa18c39a4f0`, plus its visual-direction and interaction-states references. Author-side field report, not a controlled comparison or human-usability evidence. No upstream or premium design skill loaded.

The maintained dashboard design/behavior contracts remain project requirements. The candidate defers to them: system typography, theme tokens, shared tabs, table frames and focus behavior are retained.

## What changed the output

Preserving meaning/uncertainty led to distinct configured, null, absent, withheld and effective-value rows. Task-first hierarchy puts digest/state/in-force/read-only before profiles. Providers retain the observation environment and policy-wide scope. Rendered verification is required rather than inferred from compilation. Proportionality avoids an invented aesthetic risk, typography dependency or second design system. Actual controls inspect fields without disabled Save/catalog controls implying absent capabilities.

## Improvements and additional skills

Add a conditional read-heavy-interface checklist: concealed reads, obsolete results, scope retirement, source identity, configured/effective/observed distinctions. Direct builders to host API/cache owners rather than defining a competing policy.

Add an early verification-tool check. Existing Windows dependencies supported typechecking but lacked the build's native binding; pinned Node 22 lived in Snap Docker rather than Docker Desktop. Locating it earlier would avoid a failed Windows test invocation.

No separate coding/testing skill was necessary: repository code, tests and pinned tools provide that procedure. An engineering companion could help with component extraction, validation boundaries and selecting meaningful tests, provided it does not impose a framework or duplicate host rules. Independent review remains a repository requirement.

Independent review exposed concrete gaps in the initial implementation: retirement must be checked after awaited work and before the next read, and replacing a source must synchronously exclude its predecessor's displayed result. A useful engineering companion would teach these guarantees and test noncooperative asynchronous sources. The design skill's general stale-response advice helps but does not replace such tests. It also should encourage semantically coherent fixtures: an initial long-name fixture changed the name without changing its field locators and exceeded the safe-name bound. Those findings are corrected and retained in review evidence; they are not evidence that this skill outperforms another.

## Noise, conflicts and reuse

Rendered phone verification exposed a pre-existing shared navigation issue: the open sidebar covered its own header toggle. The candidate's shared-owner guidance led to a small Shell close action, preserving selection and returning trigger focus, with sibling-screen verification. Test drivers also needed to distinguish duplicate disclosed warnings and open navigation before selecting a concealed theme control; compilation alone missed both.

Marketing/asset examples contribute little here, but remain compact and impose no inappropriate choices. No instruction conflicts with the dashboard or offline gate observed. I would load the candidate again. This is a qualitative assessment, not demonstrated superiority over another skill.

## Context feedback

The brief's separation of fixtures, adoption, live reads, Save and catalog ownership should be standing guidance. Appendix A is a shape inventory, not a complete machine-valid contract. Strict fixture validation must not become accidental C0 acceptance. Include sanitized Engine examples with the later change note, especially empty/default output.

The named port must be checked for availability and existing ownership. Prerequisite/main CI status can change during work; report current evidence instead of treating the brief's readiness statements as execution evidence.
